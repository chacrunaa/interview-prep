> Describe an event-driven system you worked on. How did you handle at-least-once delivery and make consumers idempotent?
Most event-driven work I've done runs on RabbitMQ and Kafka. A concrete case was at Carprice, where photo uploads for car inspections (about 10K a day) used to block the mobile app because the server processed everything synchronously, so I moved that to async: the photo goes straight to S3 and a consumer picks it up from the queue and does the processing from there. At Nedra Digital queues sat between the microservices too, and I put queue depth and lag into the observability stack so I could see a backlog building up before it turned into an incident. For at-least-once I just assume redelivery will happen and design consumers around it: dedupe on a stable key before doing anything with side effects, keep the processing step idempotent (upsert instead of insert, or check against a processed-ids/idempotency key), and make sure retries or manual redelivery can't produce duplicate side effects. I did the same thing on the API side at Syndicate Group with idempotency keys at the API and storage level to kill duplicate charges on payment operations, so it's really the same pattern, just applied on the consumer side instead of the endpoint.

> Have you built or run multi-tenant services, or put OAuth2/OIDC in place? Tell us what you did.
Yes, this is actually real hands-on experience for me. I worked deeply with Keycloak on a large enterprise platform: one shared secured network perimeter covering around 25 large projects, each with its own team of roughly 12-16 people, and authentication was common across all of them instead of every project rolling its own. A good chunk of what I did there was exactly the cross-team architecture side of multi-tenancy: working out with the identity team and the other project teams where and how users should live at the auth-provider level so 25 teams weren't each inventing their own user store, plus the balancer/gateway layer so requests got routed and authenticated consistently across that many services. Those decisions weren't mine alone, they came out of working cross-team with whoever owned identity and the other consuming services, but I was directly in the room shaping them. So shared-identity, multi-tenant-style architecture is something I've actually lived in, not just something adjacent to what I've done.

> How do you use coding agents in your daily work? How do you set constraints and check the output for correctness, security and tests?
I use Claude Code daily from the terminal for boilerplate, tests, refactoring and digging through unfamiliar code, while design decisions stay with me. Constraints are mostly project context: a rules file with our architecture conventions, community skills I fork and tune to the project, restricted permissions with no access to secrets or prod, and small scoped tasks where the agent shows a plan before touching code. I read every diff like a PR from a junior, check that tests actually cover behavior instead of just passing, and run golangci-lint with gosec, govulncheck and a security-review agent on top, and the same checks gate CI, so nothing lands just because an agent said it's fine.
