Optimistic locking через версию: конфликт версии ≠ ошибка сериализации

Одна победа этого урока: ты пишешь UPDATE ... WHERE id = $1 AND version = $2 и по одному признаку понимаешь, что делать при неудаче: конфликт заметило приложение (0 строк) или база (ошибка 40001). От этого зависит, повторять ли транзакцию и кто решает, что делать дальше.

Продолжение цепочки: «Read Committed» → «SELECT FOR UPDATE» → «FOR UPDATE против UPDATE» → этот. В 0006 было два лекарства от потерянного обновления: считать в SQL или заблокировать заранее. Здесь третье: не блокировать, а проверить при записи.

Аналогия

Вы с коллегой открыли один и тот же документ в редакторе. Внизу написано: «версия 7». Ты правишь 10 минут и жмёшь «Сохранить». Редактор проверяет: документ всё ещё версии 7? Если да — сохраняет и ставит версию 8. Если коллега успел сохранить раньше и там уже 8 — редактор говорит: «документ изменился, пока вы его редактировали», и твоя правка не затирает чужую.

Никто ничего не запирал на эти 10 минут. Ставка «оптимистичная»: скорее всего, никто не помешает, а если помешал — узнаем в момент сохранения.

Пессимистичная блокировка (FOR UPDATE) — это повесить на документ замок на все 10 минут. Надёжно, но коллега всё это время ждёт.

Формально

Optimistic locking (оптимистичная блокировка) — способ защиты от потерянного обновления, при котором строка между чтением и записью не блокируется, а у неё есть поле-счётчик version. Запись проходит, только если версия не изменилась с момента чтения, и при этом увеличивает её на 1.

Слово «блокировка» в названии сбивает: никакой блокировки нет. Это проверка при записи. Именно так это и стоит сказать на собесе.

Как реализовать

Шаг 1. Колонка в таблице:

ALTER TABLE orders ADD COLUMN version int NOT NULL DEFAULT 1;

Шаг 2. Читаем строку вместе с версией. Блокировки нет — это обычный SELECT, и чтение может быть хоть в другом HTTP-запросе (форма, которую человек правит 10 минут):

SELECT id, address, version FROM orders WHERE id = $1;   -- version = 7

Шаг 3. Пишем, проверяя версию прямо в WHERE и увеличивая её в SET:

UPDATE orders
SET address = $2, version = version + 1
WHERE id = $1 AND version = $3;     -- $3 = 7, то, что прочитали

Шаг 4. Смотрим, сколько строк затронуто. Одна — победа. Ноль — кто-то успел раньше:

var ErrVersionConflict = errors.New("version conflict")

func (r *Repo) UpdateAddress(ctx context.Context, id int64, addr string, version int) error {
    tag, err := r.db.Exec(ctx,
        `UPDATE orders SET address = $2, version = version + 1
         WHERE id = $1 AND version = $3`, id, addr, version)
    if err != nil {
        return err
    }
    if tag.RowsAffected() == 0 {
        return ErrVersionConflict // или строку удалили - различить можно RETURNING / отдельным SELECT
    }
    return nil
}

Почему это работает даже на Read Committed, без всяких повышенных уровней изоляции: это то самое правило из урока 0005. Если две транзакции пишут одну строку одновременно, вторая ждёт блокировку строки, а потом перечитывает свежую версию и заново проверяет WHERE. А там уже version = 8, условие version = 7 ложно — 0 строк. Сама база никакой ошибки не вернула: конфликт заметил твой код по числу строк.

Ошибка сериализации — это другое

Теперь вторая половина вопроса. Ошибка сериализации (serialization failure) — это когда сама база PostgreSQL отказывается коммитить транзакцию и возвращает код SQLSTATE 40001. Бывает только на уровнях Repeatable Read и Serializable:

  • Repeatable Read: транзакция работает со снимком данных на момент своего начала. Если она пытается изменить строку, которую после этого изменила и закоммитила другая транзакция, — could not serialize access due to concurrent update. Перечитать «свежую версию», как на Read Committed, нельзя: это сломало бы обещанный снимок.
  • Serializable: вдобавок база следит за зависимостями «кто что читал и кто что писал» и рвёт одну из транзакций, если их результат не совпадает ни с одним последовательным порядком. Так ловится write skew — когда две транзакции писали разные строки, но решения принимали по данным друг друга.

И важное: после 40001 транзакция мертва. Любая следующая команда в ней получит current transaction is aborted. Остаётся только ROLLBACK.

Одной фразой: версия — это твоя собственная, ручная и точечная проверка; 40001 — общая автоматическая проверка базы, которая сама решает, кого откатить.

Когда повторять всю транзакцию

При 40001 (и при deadlock, 40P01) — всегда всю, с BEGIN. Не последний запрос, а всю транзакцию целиком, включая чтения. Причина: все решения внутри неё принимались по снимку, который оказался устаревшим. Повторишь только последний UPDATE — запишешь результат, посчитанный по старым данным, то есть получишь ту самую аномалию, от которой база тебя только что спасла. Документация PostgreSQL прямо говорит: приложение должно быть готово повторить транзакцию, и это нормальная ситуация, а не авария.

func WithRetry(ctx context.Context, pool *pgxpool.Pool, fn func(pgx.Tx) error) error {
    for attempt := 0; attempt < 5; attempt++ {
        err := pgx.BeginTxFunc(ctx, pool,
            pgx.TxOptions{IsoLevel: pgx.Serializable}, fn) // fn читает ВСЁ заново
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) && (pgErr.Code == "40001" || pgErr.Code == "40P01") {
            time.Sleep(time.Duration(10*(attempt+1)+rand.Intn(10)) * time.Millisecond)
            continue
        }
        return err // успех (nil) или ошибка, которую повтор не лечит
    }
    return errors.New("too many serialization retries")
}

Три правила, которые видно в коде: лимит попыток, пауза со случайной добавкой (иначе две транзакции снова столкнутся в ту же миллисекунду), и вся логика внутри fn — она при повторе заново читает данные и заново принимает решение.

При конфликте версии — зависит от того, откуда пришла старая версия.

  • Версию принёс пользователь (открыл форму, правил, нажал «Сохранить»). Автоматически повторять нельзя: повтор = перечитать свежую версию и всё равно записать правку пользователя поверх чужой. Это и есть потерянное обновление, просто в обход проверки. Правильно — вернуть 409 Conflict и показать человеку свежие данные. В HTTP это ещё оформляют через ETag / If-Match и ответ 412.
  • Чтение и запись делает сам сервис за одну операцию (например, пересчитать JSON-поле с настройками). Повторять можно, но повторять надо весь цикл «прочитал — решил — записал». Если в той же транзакции были другие записи, построенные на прочитанном, — откатывай и повторяй всю транзакцию, так же как при 40001.

Врезка: та же версия на Repeatable Read

Тонкость для уверенного ответа. Если транзакция на Repeatable Read делает UPDATE ... WHERE version = 7, а другая транзакция изменила эту строку после начала первой, — ты получишь не 0 строк, а 40001. Если изменение было закоммичено до начала — снимок его уже видит, version там 8, и будет 0 строк. Поэтому код с версией на Repeatable Read обязан обрабатывать оба сигнала.

Частая ошибка на собесе

«Optimistic locking — это когда база блокирует строку при чтении». Наоборот: оптимистичная блокировка ничего не блокирует, это проверка версии при записи.

Проверять версию в Go после SELECT, а потом делать UPDATE ... WHERE id = $1. Между проверкой и записью кто-то успеет. Проверка обязана быть в WHERE того же UPDATE.

Забыть version = version + 1. Версия не меняется — следующие писатели не узнают, что строку уже трогали.

Ловить 40001 и повторять только упавший запрос. Транзакция уже мертва, и даже если начать новую, решение было принято по устаревшим данным. Повторяется всё с BEGIN.

Автоматически повторять конфликт версии из пользовательской формы. Это тихо затирает чужую правку — ровно то, от чего защищались.

Отправлять письмо или сообщение в Kafka внутри повторяемой функции. При трёх повторах уйдёт три письма. Побочные эффекты — после успешного коммита или через outbox-таблицу.

Формулировка для собеса: «Optimistic locking — это поле version: читаю строку без блокировки, пишу UPDATE ... SET ..., version = version + 1 WHERE id = $1 AND version = $2. Ноль затронутых строк — конфликт, его заметило приложение, и решаю по смыслу: если версию принёс пользователь — отдаю 409, если цикл внутренний — перечитываю и повторяю. Ошибку сериализации 40001 возвращает сама база на Repeatable Read или Serializable, транзакция после неё мертва, и повторять нужно всю транзакцию с начала, с лимитом попыток и паузой, потому что все решения в ней принимались по устаревшему снимку.»
