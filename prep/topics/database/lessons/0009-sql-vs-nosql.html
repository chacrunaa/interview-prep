SQL и NoSQL: в чём разница и какие бывают NoSQL

Одна победа этого урока: ты объясняешь, что «NoSQL» — не одна технология, а четыре разные модели данных, и по описанию задачи за минуту называешь, какую из них брать и почему (или почему оставаться на SQL).

Часть банковских ответов — общие фразы без деталей, например про моделирование данных в NoSQL и масштабирование; там, где я добавляю от себя, стоит пометка «вне банка». Аналогия

SQL — это бухгалтерия со строгими бланками. Для каждого вида документа есть фиксированная форма, документы ссылаются друг на друга по номерам, а ревизор следит, чтобы нельзя было сослаться на несуществующий бланк. Любой вопрос («сколько заказов у клиентов из Минска за квартал?») можно задать, даже если его никто заранее не планировал: бланки соединяются между собой.

NoSQL — это не одна контора, а целый набор разных инструментов, у которых общее только одно: они не бухгалтерия. Каждый заточен под свой способ доставать данные:

  • Ключ-значение — гардероб: по номерку мгновенно отдают вещь, но что внутри пальто, он не знает и по содержимому не ищет.
  • Документная — папка-досье: всё про одного клиента лежит в одной папке, со вложенными листами. Взял папку — получил всё сразу.
  • Колоночная (wide-column) — огромный склад с рядами: быстро пишет и читает по адресу ряда, расставлен под очень большие объёмы и распределённость.
  • Графовая — схема связей на доске: кто с кем знаком, кто чей начальник; сильна там, где важны сами связи.

Формально

По банку, NoSQL — это СУБД, которые не используют реляционную модель данных; они рассчитаны на большие объёмы, высокую скорость и гибкую схему. Банк выделяет четыре типа:

ТипЧто хранитПримеры из банкаДля чего
Key-ValueПары «ключ → значение»Redis, RiakКэш, сессии, счётчики, очереди (Redis in-memory)
ДокументнаяJSON/BSON-документы, вложенные объекты и массивыMongoDB, CouchDBОбъекты с гибкой структурой, читаемые целиком

ГрафоваяВершины и рёбраNeo4j, ArangoDBСвязи: соцсети, рекомендации, обход графа

Про «колоночные». Под этим словом живут два разных семейства. Cassandra/HBase (wide-column) нужны для распределённой записи и чтения по ключу; ClickHouse и подобные — аналитические колоночные СУБД для агрегатов по миллиардам строк. Банк называет один пример, Cassandra. Подробнее — в уроке 0007. На собесе уточни, о каком речь.

Почему моделирование противоположное

SQL: «сначала данные, потом запросы». Раскладываешь данные по таблицам без дублирования (нормализация), а любой вопрос потом задаёшь через JOIN.

NoSQL: «сначала запросы, потом данные». Банк: денормализация нужна «для повышения производительности чтения и упрощения запросов». Данные дублируют и вкладывают так, чтобы типичный запрос читал одну запись, без соединений.

-- SQL: заказ и его позиции в трёх таблицах, читаются через JOIN
SELECT o.id, p.name, oi.qty
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.id = 101;

// MongoDB: тот же заказ одним документом, читается одной операцией
{
  "_id": 101,
  "user_id": 42,
  "items": [
    { "product_id": 3, "name": "Кофе", "qty": 2, "price": 450 },
    { "product_id": 8, "name": "Чай",  "qty": 1, "price": 300 }
  ]
}

Цена: name товара скопирован в документ. Если название товара изменится, старые заказы так и остаются со старым (для заказа это даже правильно), но в других случаях придётся обновлять копии во многих местах. Это и есть расплата за денормализацию.

Транзакции и консистентность

  • Что такое ACID (из банка): атомарность («всё или ничего»), согласованность (не нарушаются ограничения), изолированность, долговечность (после COMMIT данные переживут сбой, обеспечивается WAL).
  • Поддерживают ли NoSQL транзакции? Банк: «некоторые поддерживают, но поддержка варьируется»; многие NoSQL изначально ослабили гарантии ради масштабируемости. Конкретика: у MongoDB нет транзакций «на уровне базы», но с версии 4.0 есть многодокументные; у Redis есть MULTI / EXEC / DISCARD / WATCH, команды в EXEC выполняются как одна атомарная операция, а WATCH прерывает её, если ключ изменили. Вне банка: в Redis нет отката уже выполненных команд при ошибке внутри EXEC, это не то же самое, что откат в SQL.
  • Модели консистентности (банк): сильная (после записи все читают новое), eventual («в итоге») — изменения со временем доезжают до всех узлов, настраиваемая по уровню (Cassandra, DynamoDB), причинно-следственная и другие.

CAP-теорема

Банк формулирует так: в распределённой системе можно одновременно гарантировать только два из трёх свойств:

  • C — Consistency: все узлы видят одни и те же данные, чтение возвращает последнюю запись.
  • A — Availability: каждый запрос получает ответ, но без гарантии, что в нём самые свежие данные.
  • P — Partition tolerance: система продолжает работать при потере связи между узлами.

Как это звучит точнее (вне банка). Разрыв сети в распределённой системе неизбежен, поэтому P не выбирают, а получают. Реальный выбор — между C и A в момент разрыва: либо отказать в ответе, чтобы не отдать устаревшее (CP), либо ответить, возможно, устаревшим (AP). Фраза «выбери любые два из трёх» — это упрощение, и интервьюер часто ждёт именно уточнения.

Банк называет сценарии для NoSQL: «большие объёмы неструктурированных данных, аналитика в реальном времени, кэширование». И проблемы: сложность поддержания схемы (раз её нет в базе, она живёт в коде), миграции данных, необходимость настройки для производительности.

Код: Redis как кэш (cache-aside)

func getUser(ctx context.Context, rdb *redis.Client, db *sql.DB, id int64) (User, error) {
    key := fmt.Sprintf("user:%d", id)

    if s, err := rdb.Get(ctx, key).Result(); err == nil {
        var u User
        return u, json.Unmarshal([]byte(s), &u) // попали в кэш
    } else if !errors.Is(err, redis.Nil) {
        // Redis недоступен: идём в основную БД, а не падаем
    }

    u, err := loadUserFromPostgres(ctx, db, id) // источник правды - SQL
    if err != nil { return User{}, err }

    b, _ := json.Marshal(u)
    rdb.Set(ctx, key, b, 10*time.Minute) // с TTL, иначе кэш устареет навсегда
    return u, nil
}

Обрати внимание на роль: Redis тут не заменяет PostgreSQL, а стоит рядом с ним. По банку, Redis хранит данные в памяти (ограничен её объёмом), сложных запросов и JOIN не поддерживает, а для сохранения на диск есть RDB (снимки) и AOF (журнал операций).

Правильный ответ — не «или», а «и»

В реальных системах обычно несколько хранилищ (polyglot persistence): PostgreSQL как источник правды, Redis как кэш, возможно, Kafka между ними, поисковый или аналитический движок сбоку. Дефолт на собесе: «начинаю с PostgreSQL; NoSQL беру, когда есть конкретная причина — паттерн доступа, объём или распределённость, которых SQL не вывозит». Вне банка: PostgreSQL умеет JSONB и закрывает часть задач «документной» базы без отдельной системы.

Как ответить вслух

«SQL — реляционная модель: таблицы, фиксированная схема, JOIN и ACID; проектируют от данных, нормализуя. NoSQL — это не одна технология, а четыре модели: ключ-значение вроде Redis, документные вроде MongoDB, wide-column вроде Cassandra и графовые вроде Neo4j. Обычно схема гибкая, масштабируются горизонтально через шардинг и репликацию, проектируют от запросов с денормализацией. Платят слабее гарантиями: консистентность часто eventual, а транзакции зависят от базы. Для денег и сложных связей я бы взял SQL, для кэша — Redis, для документов с вложенностью — Mongo, и в реальной системе обычно их комбинирую».

Частая ошибка на собесе

  • «NoSQL — это быстрее и современнее». Нет: это другой набор компромиссов. Для связанных данных и произвольных запросов SQL удобнее и надёжнее.
  • «В NoSQL нет транзакций». Неверно: у части баз они есть (Mongo с 4.0, Redis MULTI/EXEC). Правильно: гарантии зависят от базы и обычно уже, чем в SQL.
  • «SQL не масштабируется горизонтально». Масштабируется: шардирование и репликация (см. topic_08), но сложнее и часто вручную. У NoSQL это заложено в архитектуру.
  • «Схемы нет, значит, она не нужна». Схема не исчезает, она переезжает в код приложения. Ошибки формата данных теперь ловит не база, а ты (банк: «сложность в поддержании схемы»).
  • Говорить «NoSQL» как о едином целом. Всегда уточняй тип: у Redis, Mongo, Cassandra и Neo4j почти ничего общего, кроме отсутствия реляционной модели.
  • Пересказать CAP как «выбери любые два». Лучше добавить, что при разрыве сети выбор идёт между C и A.
Если что-то из этого осталось непонятным — просто спроси, разберём отдельно.
