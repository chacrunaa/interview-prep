FOR UPDATE против UPDATE: обычный UPDATE тоже блокирует

Одна победа этого урока: ты перестаёшь думать, что FOR UPDATE — это «включить блокировку», и начинаешь выбирать между ним и обычным UPDATE по одному признаку: где принимается решение — в SQL или в коде на Go.

Третий урок цепочки: «Read Committed» → «SELECT FOR UPDATE на Read Committed» → этот. Примеры про PostgreSQL. Если прошлый урок оставил ощущение «значит, без FOR UPDATE строка не защищена» — этот урок как раз про то, почему это не так.

Аналогия

Та же общая доска, что и в прошлом уроке. Обычный UPDATE — это подойти и сразу зачеркнуть запись, написав новую. Табличку «занято» при этом тоже вешают — но вешают её ровно в момент, когда ты уже поднял маркер, и никто больше не успевает влезть. Табличка висит до конца твоей транзакции.

SELECT ... FOR UPDATE — это повесить табличку «занято» и отойти подумать, ничего ещё не исправляя. Доска занята, а ты в это время считаешь на бумажке, звонишь коллеге, смотришь в другую запись — и только потом пишешь.

То есть разница не в том, есть блокировка или нет. Блокировка есть в обоих случаях. Разница в том, успеваешь ли ты что-то сделать между захватом и записью.

Формально

Главная фраза, которую стоит помнить дословно (она же в банке вопросов): SELECT ... FOR UPDATE блокирует считываемые строки — точно такую же блокировку ставит обычный UPDATE, когда считывает данные для обновления.

Что это значит практически: как только UPDATE нашёл строку, он берёт на неё блокировку уровня строки и держит её до COMMIT или ROLLBACK. Второй UPDATE той же строки из другой транзакции встанет в очередь и будет ждать. Отдельный UPDATE — сам по себе атомарная операция, ему не нужна «добавка» в виде FOR UPDATE, чтобы быть безопасным.

Опасен не UPDATE, а чтение перед ним

Вот где рождается путаница. Опасность не в UPDATE, а в том, что новое значение принесли из приложения, посчитав его по устаревшему прочитанному значению.

// ПЛОХО: потерянное обновление (lost update)
var qty int
tx.QueryRow(ctx, `SELECT qty FROM stock WHERE sku = $1`, sku).Scan(&qty) // прочитали 5, блокировки нет
if qty < n { return ErrNotEnough }
tx.Exec(ctx, `UPDATE stock SET qty = $1 WHERE sku = $2`, qty-n, sku)   // пишем 4, затирая чужие -1

Две транзакции прочитали 5, обе списали по 1, обе записали 4. Одно списание потерялось. При этом UPDATE здесь честно взял блокировку и честно отработал — он просто записал ровно то число, которое ему принесли.

Два способа это вылечить, и оба рабочие:

-- Вариант 1: пусть новое значение считает сама БД
UPDATE stock SET qty = qty - $1 WHERE sku = $2 AND qty >= $1;

-- Вариант 2: сначала заблокировать, потом читать и решать
SELECT qty FROM stock WHERE sku = $1 FOR UPDATE;   -- дальше решение в Go
UPDATE stock SET qty = $1 WHERE sku = $2;

Почему первый вариант безопасен: qty - $1 вычисляется от той версии строки, которую БД перечитала после ожидания, а не от того, что лежало в памяти Go полсекунды назад. Проверка qty >= $1 тоже проверяется заново на свежей версии. Всё решение целиком живёт в одном запросе, и «между» в нём просто нет места.

Отсюда правило-однострочник: SET qty = qty - $1 безопасно, SET qty = $computed — нет.

Как узнать, что UPDATE ничего не сделал

Атомарный UPDATE ... WHERE ничего не рассказывает о причине. Он говорит только «затронуто 0 строк», а это два разных случая:

res, err := tx.Exec(ctx,
    `UPDATE stock SET qty = qty - $1 WHERE sku = $2 AND qty >= $1`, n, sku)
if err != nil {
    return err
}
if res.RowsAffected() == 0 {
    return ErrSomething // но что именно? товара нет или остатка не хватило?
}

Три способа различить:

  • RETURNING — самый дешёвый. UPDATE ... RETURNING qty делает ровно то же одним запросом, но возвращает код новое значение. Если ответ пустой — одна из двух причин, но дальше можно обойтись одним проверочным SELECT.
  • Отдельная проверка существования после нуля строк: SELECT 1 FROM stock WHERE sku = $1. Нашлось — значит, не хватило остатка.
  • FOR UPDATE — если причин отказа много и каждая со своим сообщением пользователю, читаешь строку под блокировкой и разбираешь все случаи в Go явно.

Это и есть честная причина, по которой FOR UPDATE берут даже там, где технически хватило бы одного UPDATE: не ради безопасности, а ради внятных ошибок и читаемого кода.

RETURNING: средний вариант, про который забывают

var left int
err := tx.QueryRow(ctx,
    `UPDATE stock SET qty = qty - $1
     WHERE sku = $2 AND qty >= $1
     RETURNING qty`, n, sku).Scan(&left)
switch {
case errors.Is(err, pgx.ErrNoRows):
    return ErrNotEnough   // строки нет или условие не выполнено
case err != nil:
    return err
}
// left - актуальный остаток после списания, можно писать в лог или отдавать наружу

Один запрос, одна блокировка, полная атомарность и значение в коде. На собесе это хороший ответ на «а как вы узнаёте результат, если не делаете SELECT FOR UPDATE».

Эвристика на собес: если проверку и новое значение удаётся записать в WHERE и SET — берём UPDATE. Если нет — FOR UPDATE.

Врезка: FOR UPDATE чуть строже, чем UPDATE

Одна тонкость, которая отличает уверенный ответ от зубрёжки. «Точно такая же блокировка» — упрощение. В PostgreSQL UPDATE, который не меняет ключевые столбцы (входящие в уникальные индексы, на которые ссылаются внешние ключи), берёт более слабый режим — FOR NO KEY UPDATE. Он не мешает другой транзакции вставить дочернюю строку с внешним ключом на эту.

А явный SELECT ... FOR UPDATE всегда берёт максимальный режим и такую вставку заблокирует. Поэтому FOR UPDATE «на всякий случай» в горячем месте способен создать очередь там, где обычный UPDATE её не создавал. Если нужна блокировка только от изменения самой строки, есть SELECT ... FOR NO KEY UPDATE.

Врезка: порядок строк и deadlock

Ещё одно реальное различие. При обновлении нескольких строк одним запросом порядок выбирает планировщик, а не ты:

-- A:
UPDATE accounts SET balance = balance + 10 WHERE id IN (1, 2);
-- B одновременно:
UPDATE accounts SET balance = balance - 10 WHERE id IN (2, 1);

Нет гарантии, что обе пойдут в одном порядке — возможен deadlock и ошибка 40P01 у одной из них. Когда порядок важен, его задают явно блокировкой:

SELECT id FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE;
-- дальше UPDATE, порядок захвата уже предсказуем

Это не повод обвешивать блокировками всё: для одной строки по первичному ключу deadlock-а из порядка не возникает.

Частая ошибка на собесе

«Обычный UPDATE не блокирует строку, поэтому нужен FOR UPDATE». Самая частая и самая заметная. Блокирует, и до конца транзакции.

«FOR UPDATE нужен, чтобы UPDATE стал атомарным». Отдельный UPDATE атомарен и без него. FOR UPDATE делает атомарной связку «прочитал — решил — записал», а не сам UPDATE.

«UPDATE защищает от потерянного обновления». Только если новое значение вычисляется из текущего прямо в SQL. Если его посчитали в приложении по отдельному SELECT без блокировки — это ровно тот самый lost update.

Ставить FOR UPDATE перед UPDATE той же одной строки «для надёжности». Лишний round-trip и более долгая блокировка без всякой выгоды. Если между ними нет решения, которое нельзя выразить в SQL, вторая блокировка ничего не добавляет.

Формулировка для собеса: «Обычный UPDATE сам ставит блокировку строки до конца транзакции, так что одиночный UPDATE ... WHERE уже атомарен и безопасен — особенно если новое значение считается из текущего в самом SQL, вроде SET qty = qty - $1 WHERE qty >= $1. FOR UPDATE я беру не ради блокировки как таковой, а когда решение принимается в коде между чтением и записью: это заблокировать строку заранее, чтобы прочитанное не устарело. Нужно вернуть значение — часто хватает UPDATE ... RETURNING. Потерянное обновление появляется не от UPDATE, а от чтения без блокировки перед ним.»
