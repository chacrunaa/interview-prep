Session pooling против transaction pooling: состояние живёт не дольше транзакции

Одна победа этого урока: ты знаешь одно правило — при transaction pooling всё, что должно пережить COMMIT, теряется или утекает к чужому клиенту — и по нему сам выводишь список того, что ломается: SET, advisory lock, LISTEN, временные таблицы, prepared statements.

В банке вопросов этой темы почти нет: только строка «pgBouncer для PostgreSQL» в integration/topic_07. Урок построен на документации PgBouncer и pgx (ссылки внизу).

Зачем вообще внешний пул

В PostgreSQL одно соединение — это отдельный процесс на сервере, несколько мегабайт памяти. Поэтому max_connections обычно сотни, а не тысячи. Теперь посчитай: 30 подов Go-сервиса × pgxpool на 20 соединений = 600 соединений, и большинство из них простаивают.

PgBouncer встаёт между приложением и базой: к нему подключаются 600 клиентов, а он держит к PostgreSQL, скажем, 50 настоящих соединений и раздаёт их по очереди. Главный вопрос — на сколько он отдаёт настоящее соединение клиенту. Ответ и есть режим пула.

Аналогия

Ресторан, мало столиков, много гостей.

  • Session pooling — тебе дают столик на весь вечер, пока не уйдёшь. Можешь оставить на нём пальто и записки, они дождутся. Но пока ты сидишь и думаешь, столик никому не достанется.
  • Transaction pooling — столик дают на одно блюдо. Доел — встаёшь, за стол садится следующий. Следующее блюдо тебе подадут за другим столиком. Что забыл на прошлом — либо пропало для тебя, либо досталось чужому гостю.

Есть ещё statement pooling — соединение на один запрос, транзакции из нескольких запросов запрещены. Встречается редко, достаточно знать, что он есть.

Важная деталь про Go: pgxpool держит соединения открытыми постоянно. Значит, в session mode PgBouncer просто закрепит за каждым из них серверное соединение навсегда — экономии почти нет. Поэтому на практике PgBouncer перед Go-сервисами почти всегда в transaction mode, и вся сложность урока — про него.

Одно правило вместо списка

Состояние сессии — всё, что PostgreSQL запоминает «на соединение», а не «на транзакцию». В transaction mode соединение после COMMIT уходит другому клиенту. Отсюда два симптома:

  • Пропало: твой следующий запрос попал на другое серверное соединение, где этого состояния нет.
  • Утекло: на твоём прошлом соединении состояние осталось, и его получил чужой клиент.

Код: как это выглядит в Go

Плохо: настройка сессии отдельным запросом.

// ПЛОХО: два вызова пула = возможно, два разных соединения
pool.Exec(ctx, `SET search_path = tenant_42`)
rows, _ := pool.Query(ctx, `SELECT * FROM orders`) // search_path может быть чужим или дефолтным

Неочевидный момент: это сломано даже без PgBouncer. pgxpool сам раздаёт соединения по запросам, и два вызова pool.Exec / pool.Query вполне могут уйти на разные соединения. А «утечка» тоже есть: tenant_42 останется на том соединении, и его получит следующий запрос другого пользователя. По сути, Go-пул уже ведёт себя как transaction pooling.

Хорошо: всё состояние — внутри транзакции и LOCAL.

err := pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
    // живёт до COMMIT/ROLLBACK, на следующего клиента не утечёт
    if _, err := tx.Exec(ctx, `SELECT set_config('search_path', $1, true)`, schema); err != nil {
        return err
    }
    if _, err := tx.Exec(ctx, `SET LOCAL statement_timeout = '2s'`); err != nil {
        return err
    }
    _, err := tx.Exec(ctx, `UPDATE orders SET status = 'paid' WHERE id = $1`, id)
    return err
})

set_config(..., true) — то же, что SET LOCAL, только позволяет передать значение параметром. Так же передают app.user_id для политик Row Level Security.

Advisory lock для «только один воркер выполняет задачу»:

// ПЛОХО в transaction mode: блокировка висит на соединении, которое уже обслуживает чужих
pool.Exec(ctx, `SELECT pg_advisory_lock(42)`)
doWork()
pool.Exec(ctx, `SELECT pg_advisory_unlock(42)`) // скорее всего, уйдёт на другое соединение

// ХОРОШО: блокировка транзакции, снимется на COMMIT сама
pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
    var got bool
    if err := tx.QueryRow(ctx, `SELECT pg_try_advisory_xact_lock(42)`).Scan(&got); err != nil || !got {
        return err
    }
    return doWorkInTx(tx)
})

Prepared statements и pgx

Самая частая реальная поломка. pgx по умолчанию кэширует prepared statements: первый раз готовит запрос на соединении, дальше выполняет по имени. Через PgBouncer в transaction mode подготовлен он на одном серверном соединении, а выполнить его пытаются на другом — там такого имени нет (или, наоборот, уже есть). В логах это выглядит как ошибки вида prepared statement "stmtcache_..." does not exist.

Два пути:

  • Новый PgBouncer: начиная с версии 1.21 он сам отслеживает prepared statements уровня протокола, если включить max_prepared_statements. Тогда pgx можно оставить как есть.
  • Старый PgBouncer: переключить pgx на режим без кэша.
cfg, _ := pgxpool.ParseConfig(dsn)
cfg.ConnConfig.DefaultQueryExecMode = pgx.QueryExecModeExec // без именованных prepared statements
pool, _ := pgxpool.NewWithConfig(ctx, cfg)

Как это обычно устроено в проде

  • Обычные запросы сервиса → PgBouncer в transaction mode.
  • Миграции, LISTEN, долгие сессионные advisory-блокировки, ручные сессии в psql → напрямую в PostgreSQL (или через отдельный пул в session mode). Часто это просто второй DSN в конфиге.

Это и есть ответ на вопрос «какие ограничения накладывает»: приложение должно быть stateless по отношению к соединению — не рассчитывать, что следующий запрос попадёт туда же, куда предыдущий, и не оставлять на соединении ничего после транзакции.

Частая ошибка на собесе

«Transaction pooling — это пул, где каждый запрос в транзакции». Нет: это про то, на сколько закрепляется серверное соединение — на одну транзакцию.

«В transaction mode нельзя пользоваться транзакциями». Наоборот, транзакции работают полностью — ломается только то, что живёт дольше транзакции.

«Если PgBouncer нет, можно делать SET отдельным запросом». С pgxpool или database/sql — тоже нельзя: два вызова пула могут попасть на разные соединения. Нужна транзакция или явно взятое соединение (pool.Acquire).

Путать два пула. pgxpool — пул внутри одного процесса Go. PgBouncer — общий пул между всеми процессами и базой. Они стоят друг за другом, и один не заменяет другой.

Формулировка для собеса: «В session pooling серверное соединение закрепляется за клиентом до его отключения — работает всё, но экономии мало, особенно с Go-пулами, которые держат соединения открытыми. В transaction pooling соединение даётся на одну транзакцию, после COMMIT уходит другому клиенту — экономия большая, но всё сессионное состояние либо теряется, либо утекает: SET, сессионные advisory-блокировки, LISTEN, временные таблицы, prepared statements. Поэтому состояние держу внутри транзакции — SET LOCAL, pg_advisory_xact_lock, — для pgx включаю поддержку prepared statements в PgBouncer 1.21+ или выключаю кэш, а миграции и LISTEN пускаю напрямую в базу.»
