Виды связей: где лежит внешний ключ

Одна победа этого урока: услышав описание предметной области, ты за минуту говоришь сколько нужно таблиц, в какой из них лежит внешний ключ и какие ограничения его стерегут.

Вырос из твоего вопроса «все виды связей и есть по факту JOIN между двумя таблицами?». Короткий ответ был: связь живёт в схеме, JOIN — в запросе, и «между двумя таблицами» верно не всегда. Здесь это разобрано целиком. Опирается на topic_01_relational_sql.md («Виды связанности таблиц?»), topic_03_joins_set_operations.md (ключи и ограничения) и topic_07_database_design_normalization.md (суррогатные и естественные ключи).

Аналогия

Связь — это записка «кому я принадлежу». И единственный вопрос, который надо себе задать: в какой из таблиц эта записка физически лежит?

  • Заказ принадлежит пользователю. Записка лежит в заказе: «я от пользователя №7». Таких записок может быть сколько угодно, и все укажут на седьмого. Это и есть «один ко многим» — больше в нём ничего нет.
  • Заказ содержит много товаров, а товар встречается во многих заказах. Записку положить некуда: в одну ячейку список не влезает, а положить её и там, и там — значит хранить одно и то же дважды. Поэтому берут отдельный блокнот пар: «заказ 10 — товар 3», «заказ 10 — товар 8». Блокнот — это третья таблица.
  • У сотрудника есть руководитель, который тоже сотрудник. Записка лежит в той же таблице и указывает на неё же.

Отсюда правило: записка всегда лежит на стороне «много». Если оба конца «много» — нужна третья таблица.

Формально

Связь в реляционной БД реализуется через FOREIGN KEY — это, как формулирует банк вопросов, ссылка на первичный ключ другой таблицы, обеспечивающая целостность данных. Вид связи задаётся двумя вещами: где лежит внешний ключ и какие ограничения на него наложены.

Полный набор ограничений целостности из банка: NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, CHECK, DEFAULT. Для связей нужны три первых плюс сам FOREIGN KEY — и этого достаточно, чтобы выразить любой вид.

Один ко многим (1:N) — базовый случай

CREATE TABLE users (
    id    bigserial PRIMARY KEY,
    email text NOT NULL UNIQUE
);

CREATE TABLE orders (
    id      bigserial PRIMARY KEY,
    user_id bigint NOT NULL REFERENCES users(id),  -- вот и вся связь
    total   numeric(12,2) NOT NULL
);

Одна строка, один внешний ключ в дочерней таблице. 90% связей в любой продуктовой схеме — именно такие.

Про «Many-to-One». В банке вопросов в ответе на «Виды связанности таблиц?» перечислено четыре пункта, и последний — «Многие ко многим (Many-to-One)». Это опечатка в двух местах. Many-to-One — не отдельный вид, это та же связь 1:N, только описанная со стороны ребёнка: «много заказов → один пользователь». На собесе называй три вида и добавляй самоссылку как четвёртый случай — это звучит сильнее, чем заученный список из четырёх.

Один к одному (1:1) — это 1:N плюс UNIQUE

Отдельного механизма для 1:1 в SQL нет. Берётся та же связь и запрещается «много»:

-- Вариант 1: внешний ключ с UNIQUE
CREATE TABLE user_profiles (
    id      bigserial PRIMARY KEY,
    user_id bigint NOT NULL UNIQUE REFERENCES users(id),  -- UNIQUE и делает связь 1:1
    bio     text
);

-- Вариант 2: общий первичный ключ, он же внешний (чище и дешевле)
CREATE TABLE user_profiles (
    user_id bigint PRIMARY KEY REFERENCES users(id),
    bio     text
);

Второй вариант лучше: PRIMARY KEY сам даёт и уникальность, и NOT NULL, и индекс, и лишнего столбца id не появляется.

Зачем вообще разносить на две таблицы то, что можно держать в одной:

  • вынести редко читаемые или тяжёлые колонки (большой текст, blob), чтобы основная таблица осталась узкой и быстрой;
  • разные права доступа: паспортные данные отдельно от профиля;
  • блок данных существует не у всех строк — заполнен у меньшинства.

Многие ко многим (N:M) — три таблицы и два JOIN

Вот где ломается интуиция «связь = две таблицы». Положить внешний ключ некуда ни в одну из сторон, поэтому заводят связующую таблицу (junction):

CREATE TABLE order_items (
    order_id   bigint NOT NULL REFERENCES orders(id),
    product_id bigint NOT NULL REFERENCES products(id),
    qty        int NOT NULL CHECK (qty > 0),
    price      numeric(12,2) NOT NULL,     -- атрибут самой связи
    PRIMARY KEY (order_id, product_id)     -- защита от дублей пары
);

SELECT o.id, p.name, oi.qty
FROM orders o
JOIN order_items oi ON oi.order_id = o.id       -- два JOIN, не один
JOIN products    p  ON p.id = oi.product_id;

Два важных момента:

Составной первичный ключ обязателен. Без него ничто не мешает вставить пару «заказ 10 — товар 3» дважды, и количество товара в заказе поедет.

Атрибуты связи кладутся сюда же. qty, цена на момент покупки, дата добавления — это свойства не заказа и не товара, а именно их пары. В «чистой» связи между двумя таблицами им было бы негде лежать, и это дополнительный довод в пользу связующей таблицы, даже когда она кажется лишней.

Самоссылка: иерархия в одной таблице

CREATE TABLE categories (
    id        bigserial PRIMARY KEY,
    parent_id bigint REFERENCES categories(id),  -- NULL = корень дерева
    name      text NOT NULL
);

-- Один уровень вверх: self-join
SELECT c.name AS child, p.name AS parent
FROM categories c
LEFT JOIN categories p ON p.id = c.parent_id;

Связь есть, второй таблицы нет. parent_id IS NULL помечает корень — здесь NULL несёт смысл «родителя нет».

Важное ограничение: такой self-join поднимает ровно на один уровень. Для всего дерева нужен рекурсивный запрос (WITH RECURSIVE), и на собесе это хороший повод упомянуть, что количество уровней в SQL заранее не задано.

Обязательная связь или нет — решает NULL

Банк вопросов спрашивает об этом прямо: «Может ли значение в столбце с ограничением FOREIGN KEY равняться NULL?» Ответ: да, если на столбец не наложен NOT NULL. И это не мелочь — именно так задаётся обязательность связи:

Ограничения на FKЧто получилосьПример
NOT NULL REFERENCES1:N, связь обязательнау заказа всегда есть пользователь
REFERENCES (NULL разрешён)0..N, связь необязательнау категории может не быть родителя
NOT NULL UNIQUE REFERENCES1:1, профиль есть всегдастрока без профиля не создаётся
UNIQUE REFERENCES0..1, профиль опционаленпрофиль заполняют не все

Последняя строка работает благодаря тому, что UNIQUE допускает NULL — и в PostgreSQL даже несколько разных NULL в одном столбце. Банк отмечает это как отличие от PRIMARY KEY, который NULL не разрешает вообще.

Что даёт внешний ключ помимо возможности сделать JOIN

Это главное, что стоит унести из урока. JOIN возможен и без всякого внешнего ключа — движок соединяет по любому условию. Внешний ключ нужен для другого:

  • Целостность. Нельзя вставить заказ с user_id, которого нет в users. Без FK такой мусор спокойно накопится, и обнаружится он на отчёте через полгода.
  • Правила при удалении и изменении родителя. Их задают явно:
РежимЧто произойдёт при удалении родителя
NO ACTION / RESTRICTУдаление запрещено, пока есть дети. Поведение по умолчанию
ON DELETE CASCADEДети удаляются вместе с родителем. Для order_items уместно, для orders — почти никогда
ON DELETE SET NULLСсылка обнуляется, строка остаётся. Требует, чтобы FK допускал NULL
ON DELETE SET DEFAULTПодставляется значение по умолчанию, которое тоже должно существовать в родителе
-- Позиции не живут без заказа, а заказ не исчезает вместе с пользователем
order_id   bigint NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
user_id    bigint NOT NULL REFERENCES users(id)  ON DELETE RESTRICT,
manager_id bigint          REFERENCES users(id)  ON DELETE SET NULL

Индекс на внешний ключ надо добавить руками

Факт, который на собесе выделяет отвечающего. В PostgreSQL индекс создаётся автоматически только для PRIMARY KEY и UNIQUE. FOREIGN KEY индекса не создаёт. Два последствия:

  • JOIN и запрос «все заказы пользователя 7» уходят в полное сканирование таблицы заказов;
  • DELETE или UPDATE родителя тормозит: база обязана проверить, нет ли детей, и без индекса проверяет перебором.
CREATE INDEX ON orders (user_id);   -- почти всегда нужно сразу после REFERENCES

Отдельная ловушка в связующей таблице. Составной PRIMARY KEY (order_id, product_id) даёт индекс, который работает только слева направо: «товары этого заказа» он закрывает, а «в каких заказах встречается этот товар» — нет. Для обратного направления нужен второй индекс:

CREATE INDEX ON order_items (product_id);

Почему внешний ключ ссылается на суррогатный id

Банк вопросов (topic_07) формулирует проблему естественных ключей так: ИНН или email имеют бизнес-смысл, но при изменении требуют каскадного обновления во всех дочерних внешних ключах, а текстовые ключи ещё и занимают много места в индексах.

Перевести это на язык связей: если orders.user_email ссылается на users.email, то смена почты пользователем превращается в переписывание всех его заказов. Суррогатный id не меняется никогда — поэтому связи строят по нему, а email остаётся обычным уникальным столбцом.

Связь и JOIN — всё-таки не одно и то же

СвязьJOIN

-- JOIN без всякой связи: условие по диапазону, внешних ключей тут нет вовсе
SELECT * FROM orders o
JOIN discounts d ON o.total BETWEEN d.min_total AND d.max_total;

И наоборот: связь есть, а JOIN не делается — данные достают двумя запросами и склеивают в Go. Так часто поступают, чтобы не тащить размноженные строки по сети.

Частая ошибка на собесе

«Многие-ко-многим между двумя таблицами». Негде хранить внешний ключ. Нужна третья, связующая таблица — и это первое, что проверяют вопросом про заказы и товары.

«Один-к-одному — это просто внешний ключ». Без UNIQUE это обычное 1:N: ничто не помешает создать второй профиль тому же пользователю.

«Many-to-One — отдельный вид связи». Это 1:N со стороны ребёнка.

«Внешний ключ создаёт индекс». Нет, только PRIMARY KEY и UNIQUE. Классический вопрос «почему JOIN по FK медленный».

«Внешний ключ нужен, чтобы делать JOIN». JOIN работает и без него. FK — про целостность и каскады.

Забыть составной PK в связующей таблице. Схема выглядит правильной, а дубли пар попадают в неё молча.

Мелочь про формулировки: банк говорит, что PRIMARY KEY создаёт кластерный индекс, а UNIQUE — некластерный. Это верно для MySQL и SQL Server. В PostgreSQL кластерных индексов в этом смысле нет: все индексы отдельные от таблицы. Если собес по PostgreSQL — эту часть ответа лучше не произносить.

Формулировка для собеса: «Связей три вида, и все они выражаются одним механизмом — внешним ключом на стороне "много". Один-ко-многим — просто FK в дочерней таблице. Один-к-одному — тот же FK плюс UNIQUE, а чище — когда внешний ключ сам является первичным. Многие-ко-многим напрямую выразить нельзя, внешний ключ некуда положить, поэтому нужна третья связующая таблица с составным первичным ключом из двух FK — и туда же удобно складывать атрибуты самой связи, вроде количества и цены. Отдельный случай — самоссылка для иерархии. Обязательность связи задаёт NOT NULL на внешнем ключе. И две вещи, о которых забывают: внешний ключ нужен не для JOIN, а для целостности и каскадов, а индекс на него в PostgreSQL надо создавать руками.»
