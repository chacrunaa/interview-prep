Почему колоночную базу не берут под выборки по ключу

Одна победа этого урока: ты можешь вслух объяснить механизм, из-за которого «дай мне строку с id = 42» в ClickHouse работает хуже, чем в PostgreSQL, — и не попадаешься на «данных много, значит нужна колоночная».

Урок построен вокруг одной фразы из банка вопросов (db/column/clickhouse.md): «не следует использовать колоночные базы для случаев с обычными выборками по ключу и известными структурами запросов. Для этого лучше подойдут обычные (строчные) СУБД». Фразу легко запомнить, но на собесе спросят «почему» — вот про это.

Аналогия

Строчная база — картотека. Один клиент — одна карточка, на ней сразу имя, телефон, адрес, баланс. Нужен клиент №42 — нашёл один ящик, достал одну карточку, всё при тебе.

Колоночная база — отдельные шкафы под каждое поле. Все имена лежат в шкафу «имена», все телефоны — в шкафу «телефоны», все балансы — в шкафу «балансы», каждый по порядку номеров.

  • «Какая сумма балансов у всех клиентов?» — открыл один шкаф «балансы» и прошёл его насквозь. Остальные тридцать шкафов не трогал вообще. Это чудовищно быстро, и в этом вся сила колоночной базы.
  • «Дай карточку клиента №42» — надо обойти все тридцать шкафов и в каждом найти ячейку №42. Карточки целиком тут просто не существует, её каждый раз собирают заново.

И добавь к этому, что в каждом шкафу значения лежат не по одному, а склеенными пачками в сжатом виде: чтобы добраться до ячейки №42, пачку нужно сначала распаковать целиком.

Формально

Строчная (row-oriented) СУБД — PostgreSQL, MySQL. Строка лежит на диске целиком, подряд. Прочитал одну страницу — получил всю строку со всеми колонками.

Колоночная (columnar) СУБД — ClickHouse, Vertica. Каждая колонка хранится отдельно: по сути, отдельная однотипная таблица из своих значений плюс первичный ключ. Отсюда и преимущества: читаются только нужные колонки, однотипные данные сжимаются в разы лучше, а добавление колонки в огромную таблицу происходит мгновенно (новой колонке просто нечего переписывать).

Терминология, которую ждут на собесе:

  • OLTP (Online Transaction Processing) — классические строчные СУБД. Поток мелких транзакций, клиенту нужен максимально быстрый ответ. Продуктовая нагрузка: заказы, пользователи, корзины.
  • OLAP (Online Analytical Processing) — колоночные. Сложные аналитические запросы с агрегацией, фильтрами и сортировками по большим объёмам: отчёты, дашборды, data mining.

Механизм: почему именно выборка по ключу страдает

Три причины, и на собесе лучше назвать их по именам.

1. Разреженный индекс

В PostgreSQL индекс плотный: в нём есть запись на каждую строку. Поиск по id = 42 — это несколько шагов по B-tree и чтение одной страницы.

В ClickHouse индекс разреженный (sparse): он хранит засечку не на каждую строку, а на гранулу — блок из многих тысяч строк (по умолчанию 8192). Индекс говорит лишь «твой id где-то в этой грануле». Дальше гранулу надо прочитать и просканировать. Отсюда прямая цитата из банка: «разреженный индекс. Если вам нужна одна строчка, то вы много чего лишнего прочитаете».

2. Чем шире таблица, тем дороже одна строка

Строку надо собрать из колонок. Тридцать колонок — это тридцать отдельных мест на диске, тридцать чтений и тридцать распаковок сжатых блоков. В строчной базе это было одно чтение.

Получается перевёрнутая логика: SELECT * FROM t WHERE id = 42 — это худший возможный запрос для колоночной базы и совершенно обычный для строчной.

3. Нет транзакций и точечных UPDATE/DELETE

ClickHouse — реляционная СУБД с SQL, но без транзакций и без точечных UPDATE и DELETE. Нет оконных функций и полноценного оптимизатора. То есть обычная продуктовая логика — «списать остаток под блокировкой», «перевести заказ в paid» — в нём просто не выражается. Всё, что ты разбирал в уроках 0005 и 0006, там недоступно в принципе.

А при чём тут «известные структуры запросов»?

Это вторая половина фразы, и её почти никогда не проговаривают. Она не про скорость, а про предсказуемость.

Если ты заранее знаешь, какие будут запросы — «список статей, отсортированный по дате», «заказы пользователя за месяц» — то под каждый такой запрос в строчной базе строится индекс, и он решает задачу. Можно даже сделать покрывающий индекс и получить ровно то же «читаем только нужные колонки», ради чего берут колоночную.

Колоночная база сильна там, где заранее придумать индекс нельзя: аналитик каждый день приходит с новым разрезом, фильтром и группировкой, и индексов под все комбинации не бывает. Колоночная база обходится без них: она просто очень быстро читает нужные столбцы насквозь.

Критерий выбора — не объём данных, а форма запросов. Известные запросы по ключу → строчная база с индексами. Непредсказуемые агрегации по широким срезам → колоночная.

Код: что ломается, если взять ClickHouse под продуктовую таблицу

// Привычный продуктовый код — в колоночной базе рассыпается целиком
func (s *Service) Pay(ctx context.Context, orderID int64) error {
    return s.db.WithTx(ctx, func(tx Tx) error {          // 1. транзакций нет
        var status string
        err := tx.QueryRow(ctx,
            `SELECT status FROM orders WHERE id = $1 FOR UPDATE`, // 2. блокировок нет,
            orderID).Scan(&status)                                //    да и выборка по id
        if err != nil {                                           //    читает целую гранулу
            return err
        }
        if status != "new" {
            return ErrWrongStatus
        }
        _, err = tx.Exec(ctx,
            `UPDATE orders SET status = 'paid' WHERE id = $1`,  // 3. точечного UPDATE нет
            orderID)
        return err
    })
}

Отдельная засада: уникальность по id колоночная база тоже не гарантирует. В ClickHouse движок ReplacingMergeTree убирает дубликаты асинхронно, при слиянии частей, поэтому сразу после вставки запрос честно вернёт тебе две версии строки. Для продуктового кода это означает «первичного ключа в привычном смысле нет».

Правильный ответ — не «или», а «и»

На собесе выигрывает ответ, в котором обе базы живут рядом. Это тот же CQRS: нормализованная строчная база как модель записи и денормализованная аналитическая как модель чтения.

Go-сервис ──запись──► PostgreSQL        (заказы, пользователи: транзакции, FOR UPDATE)
    │
    └──событие──► Kafka ──► ClickHouse   (события и агрегаты: отчёты, дашборды)

Банк вопросов формулирует это так: разделение модели записи (нормализованная реляционная БД) и модели чтения (денормализованные плоские документы в Elasticsearch / ClickHouse / Redis). Там же оговорка, зачем это нужно: в чистом OLTP высокая нормализация даёт целостность, но запрос, собирающий десятки таблиц через JOIN на миллиардах строк, упирается в задержки.

Цена этого решения — задержка согласованности: аналитика отстаёт от продуктовой базы на секунды или минуты. Для отчётов это нормально, для «показать пользователю его собственный только что созданный заказ» — нет.

Врезка: «колоночные» — это два разных семейства

Тонкость, на которой легко запутаться, потому что сам банк вопросов перечисляет их вперемешку. В db/column/index.md как колоночные названы Cassandra, HBase, Bigtable и Vertica, но это не одно и то же:

Колоночные OLAPWide-column (широкие колонки)
ПримерыClickHouse, Vertica, BigQuery, DruidCassandra, HBase, Bigtable
Как храняткаждая колонка отдельно по всей таблицестроки по ключу, колонки группами внутри
Выборка по ключуплохо, это их слабое местохорошо, это их основной сценарий
Произвольные агрегацииих главная силаплохо, нужен заранее заданный ключ доступа

То есть у Cassandra ограничение ровно противоположное: она как раз про доступ по ключу, но запрос, не попадающий в заложенный ключ партиционирования, в ней сделать трудно. Правило урока относится к первой колонке таблицы.

Частая ошибка на собесе

«Данных много — значит, нужен ClickHouse». Объём сам по себе ничего не решает. Терабайтная таблица пользователей, которую читают по id, остаётся задачей для PostgreSQL.

«Колоночная быстрее, возьмём её везде». Быстрее на агрегации по нескольким столбцам из множества строк. На «одна строка целиком» — медленнее, и тем медленнее, чем больше в таблице колонок.

«ClickHouse — это NoSQL». Он реляционный и с SQL. Отсутствуют транзакции, точечные UPDATE/DELETE и оконные функции — но это не делает его NoSQL.

Назвать преимущество, не назвав механизм. «Колоночная хорошо сжимает» — половина ответа. Хорошо сжимает потому что в одной колонке лежат однотипные, часто повторяющиеся значения, а читает мало потому что не нужные запросу колонки вообще не трогает с диска.

Формулировка для собеса: «Колоночная база хранит каждую колонку отдельно, поэтому читает с диска только нужные столбцы и очень хорошо их сжимает — это даёт огромный выигрыш на аналитических агрегациях. Но строки целиком в ней нет, её собирают из всех колонок, а индекс разреженный, на гранулы по тысячам строк. Поэтому выборка по ключу читает много лишнего, и чем шире таблица, тем хуже. Плюс нет транзакций и точечных UPDATE. Если запросы известны заранее и идут по ключу, строчная база с индексом сделает это дешевле. Я бы держал продуктовые данные в PostgreSQL, а события и агрегаты отливал в ClickHouse — по сути CQRS, ценой задержки согласованности.»
