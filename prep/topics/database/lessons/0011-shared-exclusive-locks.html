Shared и exclusive lock: это sync.RWMutex, только для строк

Одна победа этого урока: ты рисуешь по памяти таблицу совместимости 2×2 (кто кого пускает) и говоришь, почему в PostgreSQL обычный SELECT всё равно не ждёт ни одну из этих блокировок.

Связано с уроками «SELECT FOR UPDATE» и «FOR UPDATE против UPDATE». Там был только один вид блокировки строки — для записи. Здесь появляется второй, и становится видно, что FOR UPDATE — это просто exclusive lock.

Аналогия

Ты пишешь на Go, так что аналогия уже знакома: sync.RWMutex.

var mu sync.RWMutex

mu.RLock()   // много горутин могут держать одновременно: все только читают
mu.RUnlock()

mu.Lock()    // только одна горутина, и пока она держит - ни RLock, ни Lock не пройдут
mu.Unlock()

RLock — это и есть shared lock: «я читаю и хочу, чтобы никто не менял, пока я не закончу; читать вместе со мной — пожалуйста». Lock — exclusive lock: «я меняю, никто больше не держит этот замок».

Только в базе замок вешается не на структуру в памяти, а на конкретную строку (или на таблицу), и снимается не когда ты вызвал Unlock, а в конце транзакции — на COMMIT или ROLLBACK.

Формально

  • Shared lock (S, разделяемая, совместная блокировка) — другие транзакции могут взять на эту строку такую же S-блокировку, но не могут её изменить и не могут взять X-блокировку.
  • Exclusive lock (X, исключительная блокировка) — никто другой не может взять на эту строку ни S, ни X, пока она держится.

Вся тема укладывается в одну таблицу. Её стоит уметь нарисовать на доске:

Уже держат →
Хочу взять ↓		SX
S✅ можно⏳ жду
X⏳ жду⏳ жду

Правило запоминается так: совместимы только два чтения. Всё, где есть запись, — ждёт.

И ещё одно слово из банка вопросов: InnoDB (и PostgreSQL тоже) держит блокировки до конца транзакции и снимает все разом. Это называют двухфазной блокировкой (2PL): сначала только набираешь блокировки, потом на коммите отпускаешь всё сразу.

Как это выглядит в SQL

PostgreSQLMySQL InnoDB
Shared lock на строкуSELECT ... FOR SHARESELECT ... FOR SHARE (8.0), раньше LOCK IN SHARE MODE
Exclusive lock на строкуSELECT ... FOR UPDATESELECT ... FOR UPDATE
Берут X самиUPDATE, DELETEUPDATE, DELETE

То есть ничего нового ты не учишь: FOR UPDATE из прошлых уроков — это и есть exclusive lock, а обычный UPDATE берёт такой же. Новое только одно — FOR SHARE.

Тонкость для PostgreSQL: там на самом деле четыре режима блокировки строки — FOR KEY SHARE < FOR SHARE < FOR NO KEY UPDATE < FOR UPDATE. Это та же идея S/X, только раздробленная: UPDATE, не трогающий ключевые столбцы, берёт FOR NO KEY UPDATE (это было во врезке урока 0006). На собесе достаточно сказать, что они есть и что это уточнение S/X.

Главное: обычный SELECT в эту таблицу не входит

Вот где ломается большинство ответов. В учебниках (и в банке вопросов, в dBTheory/transactions.md) описан классический подход: каждое чтение берёт S-блокировку, поэтому писатель ждёт читателей, а читатели ждут писателя.

В PostgreSQL и в InnoDB (на уровнях до Repeatable Read включительно) так не работает. Там MVCC: обычный SELECT читает снимок данных и никаких блокировок строк не берёт. Поэтому:

-- Транзакция A
BEGIN;
UPDATE accounts SET balance = 0 WHERE id = 1;  -- X-блокировка на строку 1

-- Транзакция B, параллельно
SELECT balance FROM accounts WHERE id = 1;            -- ✅ сразу, видит старое значение
SELECT balance FROM accounts WHERE id = 1 FOR SHARE;  -- ⏳ ждёт: хочет S, а там X

Это ровно то, что было в записи после урока 0006: блокировки строк конфликтуют только с другими блокировками. Обычное чтение — не блокировка, оно никого не ждёт и никому не мешает.

Исключение, которое любят спросить: в MySQL InnoDB на уровне Serializable обычный SELECT внутри транзакции автоматически превращается в SELECT ... FOR SHARE. Вот там читатели и писатели начинают ждать друг друга — так и надо понимать фразу из банка, что exclusive lock «может блокировать и чтение в зависимости от уровня изоляции».

Когда нужен FOR SHARE

Когда тебе надо, чтобы строка не поменялась и не исчезла, пока ты делаешь что-то рядом с ней, но саму её ты менять не собираешься. Классика — родитель и потомок:

// Добавить товар в заказ, только если товар активен.
err := pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
    var active bool
    err := tx.QueryRow(ctx,
        `SELECT active FROM products WHERE id = $1 FOR SHARE`, productID).Scan(&active)
    if err != nil {
        return err
    }
    if !active {
        return ErrProductInactive
    }
    // до конца транзакции никто не сможет выключить или удалить товар
    _, err = tx.Exec(ctx,
        `INSERT INTO order_items (order_id, product_id) VALUES ($1, $2)`, orderID, productID)
    return err
})

Почему не FOR UPDATE: сто покупателей одновременно добавляют этот товар в корзины. С FOR SHARE они не мешают друг другу (S совместима с S). С FOR UPDATE они выстроились бы в очередь по одному. А админ, который в этот момент делает UPDATE products SET active = false, подождёт всех — ему нужна X.

Внешние ключи в PostgreSQL делают то же самое сами: при вставке потомка база берёт на родителя FOR KEY SHARE, чтобы его не удалили.

Ловушка: S, а потом X — это deadlock

Самый частый практический вопрос по теме. Две транзакции:

-- A                                       -- B
SELECT ... WHERE id = 1 FOR SHARE;  -- S   SELECT ... WHERE id = 1 FOR SHARE;  -- S, можно
UPDATE ... WHERE id = 1;  -- хочу X,       UPDATE ... WHERE id = 1;  -- хочу X,
                          -- жду S от B                              -- жду S от A
                          -- 💥 deadlock, одну база откатит с 40P01

Обе честно держат S (это разрешено), обе хотят повысить до X, и каждая ждёт, пока другая отпустит свою S. Вывод: если собираешься менять строку — бери сразу FOR UPDATE, а не FOR SHARE «на время проверки». В Go то же самое: нельзя повысить RLock до Lock, не отпустив его.

Врезка: по размеру — строка или таблица

S и X описывают режим. Отдельно есть гранулярность — что блокируем:

  • Строку — то, о чём весь урок. Мелко, параллельно, но блокировок много.
  • Таблицу — LOCK TABLE, а также ALTER TABLE, который берёт самую сильную табличную блокировку и останавливает даже чтения. Отсюда страх миграций на живой базе.

В InnoDB есть ещё intention locks (IS, IX) — это табличная пометка «внутри кто-то держит S или X на строках». Нужна, чтобы LOCK TABLE не перебирал все строки, а сразу увидел, что таблица занята. Достаточно знать, что они есть и зачем.

Частая ошибка на собесе

«Shared lock — это блокировка на чтение, значит пока она есть, другие не могут читать». Наоборот: shared как раз разрешает другим читать и брать такую же S. Запрещает только менять.

«Exclusive lock блокирует все чтения строки». В PostgreSQL и InnoDB с MVCC — нет: обычный SELECT его не замечает. Ждут только FOR SHARE, FOR UPDATE, UPDATE, DELETE.

Путаться в формулировках «блокирует на запись / на чтение». В банке написано «LOCK IN SHARE MODE блокирует строки на запись», а «FOR UPDATE — на чтение». Это про то, что они запрещают другим: первая не даёт другим писать, вторая — ещё и брать блокирующее чтение. Лучше на собесе вообще не говорить «на запись / на чтение», а говорить «S совместима с S, X ни с чем».

Брать FOR SHARE, а потом обновлять ту же строку. Ведёт к deadlock при параллельных вызовах. Нужна запись — сразу X.

Формулировка для собеса: «Shared lock — разделяемая блокировка: несколько транзакций могут держать её одновременно, но никто не может изменить строку. Exclusive — только одна транзакция, несовместима ни с S, ни с X. Совместимы только две S. Держатся до конца транзакции. В PostgreSQL это FOR SHARE и FOR UPDATE, а UPDATE/DELETE берут X сами. При этом из-за MVCC обычный SELECT никаких блокировок строк не берёт и не ждёт — конфликтуют только блокировки между собой. Это как sync.RWMutex: RLock и Lock.»
