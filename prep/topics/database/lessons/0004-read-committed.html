Read Committed: чтение только зафиксированного

Одна победа этого урока: ты объясняешь простыми словами, что гарантирует Read Committed (нет «грязного» чтения), чего не гарантирует (данные могут поменяться между двумя твоими SELECT), и чем отличаются два способа его реализации — блокировки и MVCC.

Аналогия

Ты работаешь над отчётом, а коллега в соседней комнате правит общую таблицу на своём ноутбуке. Пока он не нажал «Сохранить», ты его правки не видишь: у него черновик. Как только сохранил — ты видишь новую версию.

Это и есть Read Committed: читаешь только то, что уже «сохранено» (закоммичено). Черновики чужих транзакций не видны. Но и «заморозки» нет: если ты открыл таблицу дважды, между открытиями коллега мог сохраниться, и во второй раз цифры будут другие.

Формально

Read Committed — второй по строгости снизу уровень изоляции в стандарте SQL. Он защищает от грязного чтения (dirty read): транзакция не видит данные, которые другая транзакция изменила, но ещё не зафиксировала (а вдруг откатит — тогда ты прочитал то, чего никогда не было).

Но пока идёт твоя транзакция, другая может успешно завершиться и зафиксировать изменения. В итоге твоя транзакция работает с разными наборами данных в разные моменты. Это даёт две аномалии, от которых уровень не защищает:

  • Неповторяющееся чтение (non-repeatable read): прочитал строку, повторил запрос — значение уже другое.
  • Фантомное чтение (phantom read): повторил запрос по диапазону — появились новые строки.

Пример: две сессии

Таблица accounts, у Ани на счёте 100. Слева — транзакция A (читает), справа — B (пишет).

ШагТранзакция AТранзакция B
1BEGIN;BEGIN;
2UPDATE accounts SET balance = 500 WHERE id = 1;
3SELECT balance ... → 100 (черновик B не виден)
4COMMIT;
5SELECT balance ... → 500 (изменилось внутри одной транзакции)

Шаг 3 — защита от грязного чтения работает. Шаг 5 — неповторяющееся чтение: тот же запрос в той же транзакции дал другой ответ. На Read Committed это нормально и ожидаемо.

Как реализуют: два подхода

1. Блокировки

Читающая транзакция ставит на прочитанные данные разделяемую (shared) блокировку. Пока она держится, писатель, который хочет изменить эти строки, ждёт. А пишущая транзакция блокирует изменяемые строки для читающих (на этом уровне и выше) до своего конца. Читатель не может прочитать черновик — он просто ждёт коммита.

Плюс: просто и не тратит память. Минус: читатели и писатели мешают друг другу, растёт ожидание и риск взаимной блокировки (deadlock).

2. MVCC (версионность)

Аналогия: вместо одной тетради с ластиком у каждой правки своя страница. Писатель не стирает старую страницу, а кладёт рядом новую. Читатель смотрит последнюю зафиксированную страницу и писателя не ждёт.

Формально: при каждом изменении СУБД создаёт новую версию строки. Транзакция, которая изменила данные, работает со своей новой версией. Любой другой читатель получает последнюю зафиксированную версию.

Плюс: читатели не блокируют писателей и наоборот — выше скорость. Минус: версии надо где-то хранить, отсюда расход памяти и диска (в PostgreSQL мёртвые версии убирает VACUUM, в MySQL InnoDB старые версии лежат в undo-логах).

Что происходит, когда две транзакции пишут одну строку

При MVCC блокировок на чтение нет, но две транзакции могут захотеть изменить одну и ту же строку. Тут нужно точно понимать, что отвечать, потому что учебный текст, из которого взят этот урок, обобщает.

В общем описании MVCC говорят так: та транзакция, что зафиксировалась первой, сохраняет изменения, а остальные откатываются с ошибкой вроде «Запись уже изменена». Это правило «первый коммит побеждает» (first committer wins).

Но в PostgreSQL это верно для Repeatable Read, а не для Read Committed. На Read Committed поведение мягче:

  1. Вторая транзакция при UPDATE той же строки ждёт, пока первая закоммитится или откатится.
  2. Если первая откатилась — вторая спокойно обновляет строку.
  3. Если первая закоммитилась — вторая перечитывает свежую версию строки, заново проверяет условие WHERE и применяет свой UPDATE поверх. Ошибки нет.

Ошибка could not serialize access due to concurrent update появляется на Repeatable Read и Serializable — там снимок зафиксирован, и «поверх» чужого изменения писать нельзя. Приложение обязано повторить транзакцию.

Ловушка: потерянное обновление на Read Committed

Из-за этого «перечитывания» есть тонкость. Если приложение читает значение, считает в коде и пишет обратно, обновление можно потерять:

-- Плохо: читаем, считаем в Go, пишем
SELECT balance FROM accounts WHERE id = 1;   -- 100
-- в коде: newBalance = 100 + 20
UPDATE accounts SET balance = 120 WHERE id = 1;
-- параллельная транзакция сделала то же самое с +50 и записала 150.
-- Наша запись перетёрла её. Итог: 120, а должно быть 170.

Решения на Read Committed:

-- 1. Считать в самом UPDATE: строка перечитывается после ожидания
UPDATE accounts SET balance = balance + 20 WHERE id = 1;

-- 2. Или заблокировать строку при чтении
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;

Частая ошибка на собесе

Говорить «Read Committed защищает от всех аномалий чтения». Нет: он защищает только от грязного чтения. Неповторяющееся чтение, фантомы и потерянное обновление на нём возможны.

Ещё одна: сказать «MVCC значит блокировок нет совсем». Читатели не блокируют писателей, но две записи в одну строку всё равно ждут друг друга на блокировке строки.

И третья: не знать, что Read Committed — уровень по умолчанию в PostgreSQL (в MySQL InnoDB по умолчанию Repeatable Read). Это любят спрашивать.

Формулировка для собеса: «Read Committed гарантирует, что я читаю только зафиксированные данные, то есть грязного чтения нет. Но между двумя запросами в одной транзакции другая может закоммититься, и я увижу другие данные: возможны неповторяющееся чтение и фантомы. Реализуют его либо блокировками, либо MVCC. В MVCC читатель получает последнюю зафиксированную версию и не блокирует писателей, но за это платим памятью под версии. В PostgreSQL это уровень по умолчанию, и каждый запрос видит свой снимок.»
