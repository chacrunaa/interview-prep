Как ускорить JOIN: сначала план, потом рычаг

Одна победа этого урока: на вопрос «как ускорить JOIN» ты отвечаешь не списком советов, а порядком действий: смотрю EXPLAIN ANALYZE → вижу, какой алгоритм выбран и где он страдает → дёргаю рычаг, который лечит именно эту беду. Рычагов всего пять: индекс, меньше строк, «честное» условие, статистика, память.

В уроке «JOIN в бизнесе» три алгоритма были таблицей в «Опасности 4». Здесь мы учимся их узнавать в плане запроса и лечить. Это вопрос банка «Какие 3 физических алгоритма выполнения JOIN использует оптимизатор?» плюс «Как проанализировать запрос?» из темы про индексы.

Аналогия

Тебе дали две пачки карточек: 50 заказов и 5 миллионов позиций заказов. Надо разложить позиции по заказам. Есть три способа:

  • Nested Loop — берёшь заказ и ищешь его позиции в пачке. Если пачка позиций разложена по номерам заказа с оглавлением (индекс), это 50 быстрых заглядываний. Если нет — 50 раз перебираешь 5 миллионов карточек.
  • Hash Join — выписываешь 50 номеров заказов на листок-словарь, а потом один раз проходишь всю пачку позиций и для каждой смотришь в листок. Отлично, если листок помещается на столе (в памяти). Не помещается — раскладываешь по коробкам на полу (на диске), и всё замедляется.
  • Merge Join — обе пачки уже отсортированы по номеру заказа: ведёшь два пальца сверху вниз одновременно. Быстро, но если пачки не отсортированы, сначала придётся сортировать.

Ускорить JOIN — значит понять, каким способом база сейчас раскладывает карточки, и убрать то, что ей мешает. Гадать без плана — бессмысленно.

Формально: три алгоритма и их слабое место

АлгоритмХорош, когдаСлабое местоРычаг
Nested Loopснаружи мало строк, внутри индекс по ключунет индекса внутри; база ошиблась и снаружи строк на самом деле многоиндекс, статистика

Выбирает алгоритм планировщик — по оценке, сколько строк придёт с каждой стороны. Эту оценку он берёт из статистики таблицы. Запомни эту цепочку: статистика → оценка строк → выбор алгоритма. Половина медленных JOIN ломается в её начале.

Шаг 0: измерить

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, i.sku, i.qty
FROM orders o
JOIN order_items i ON i.order_id = o.id
WHERE o.customer_id = 43;

EXPLAIN показывает план и оценки, ANALYZE реально выполняет запрос и добавляет фактические цифры, BUFFERS — сколько страниц прочитано. На что смотреть:

  • Тип узла соединения: Nested Loop, Hash Join или Merge Join.
  • rows= в оценке против rows= в actual. Расхождение в сотни раз — проблема статистики.
  • Seq Scan по большой таблице, из которой в итоге нужно мало строк, — кандидат на индекс.
  • loops= — сколько раз выполнился узел. Внутренняя сторона Nested Loop выполняется столько раз, сколько строк снаружи.
  • Batches: 8 у Hash или Sort Method: external merge Disk — не хватило памяти.

Рычаг 1: индекс на ключ соединения

Самый частый случай. Вот план того запроса:

Hash Join  (actual time=0.129..146.551 rows=40 loops=1)
  Hash Cond: (i.order_id = o.id)
  ->  Seq Scan on order_items i  (actual rows=2000000 loops=1)     -- прочитали 2 млн
  ->  Hash
        ->  Bitmap Heap Scan on orders o  (actual rows=10 loops=1)
Execution Time: 146.601 ms

Чтобы найти 40 позиций, база прочитала все 2 миллиона. Причина: по order_items.order_id нет индекса. Важно: PostgreSQL не создаёт индекс на колонку внешнего ключа автоматически — только на первичный ключ и UNIQUE. Это надо делать руками.

CREATE INDEX CONCURRENTLY order_items_order_id_idx ON order_items (order_id);
Nested Loop  (actual time=0.036..0.349 rows=40 loops=1)
  ->  Bitmap Heap Scan on orders o  (actual rows=10 loops=1)
  ->  Index Scan using order_items_order_id_idx on order_items i  (actual rows=4 loops=10)
Execution Time: 0.424 ms

Тот же запрос, в 350 раз быстрее: планировщик сам сменил Hash Join на Nested Loop, потому что теперь 10 заглядываний по индексу дешевле одного полного прохода. CONCURRENTLY — чтобы не блокировать запись в таблицу на время построения индекса на живой базе.

Усиления того же рычага: составной индекс (order_id, created_at), если по правой таблице ещё и фильтруют (правило левого префикса из банка); покрывающий индекс ... INCLUDE (sku, qty), чтобы получить Index Only Scan и не ходить в таблицу вовсе.

Рычаг 2: меньше строк и колонок на входе

  • Фильтруй как можно раньше. Селективный WHERE по одной из таблиц уменьшает то, что вообще идёт в соединение. Планировщик обычно сам проталкивает фильтры вниз, но только если они написаны так, что их можно протолкнуть.
  • Не тащи SELECT *. Для Hash Join в память кладутся строки целиком — узкие строки = маленькая хэш-таблица = не уходит на диск.
  • Агрегируй до соединения. Это лечение fan-out из урока 0003, и заодно ускорение: соединяешь 50 строк агрегата, а не 5 миллионов строк.
  • Нужна только проверка наличия — пиши EXISTS, а не JOIN + DISTINCT. EXISTS останавливается на первом совпадении (semi-join), а JOIN сначала размножает строки, потом DISTINCT их схлопывает.
-- медленно: размножили, потом схлопнули
SELECT DISTINCT c.id, c.name
FROM customers c JOIN orders o ON o.customer_id = c.id;

-- быстро: хватает первого заказа
SELECT c.id, c.name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

Рычаг 3: условие соединения, которое может использовать индекс

Из урока 0003: индекс не работает, если над колонкой функция или приведение типа.

-- индекс по b.email бесполезен
... JOIN b ON lower(a.email) = b.email
... JOIN b ON a.user_id::text = b.user_ref        -- разные типы у колонок

-- лечение: одинаковые типы в схеме или индекс по выражению
CREATE INDEX ON a (lower(email));

Ещё: Hash Join и Merge Join работают только для равенства. ON a.ts BETWEEN b.start AND b.end оставляет только Nested Loop — тут без индекса по диапазону совсем плохо.

Рычаг 4: статистика

Коварный случай — индекс есть, а запрос всё равно медленный:

Nested Loop  (rows=1) (actual rows=100000 loops=1)
  Join Filter: (im.sku = p.sku)
  Rows Removed by Join Filter: 99900000
  ->  Seq Scan on imports im  (rows=1) (actual rows=100000 loops=1)
  ->  Seq Scan on products p  (actual rows=1000 loops=100000)
Execution Time: 6939 ms

Планировщик думал, что снаружи 1 строка (rows=1), и выбрал Nested Loop: «один раз пройду 1000 товаров». А пришло 100 тысяч — и справочник товаров перечитан 100 тысяч раз. Так бывает сразу после массовой загрузки: autovacuum ещё не успел обновить статистику.

ANALYZE imports;   -- пересчитать статистику: Hash Join, 17 ms вместо 6.9 s

Тонкость: если внутри Nested Loop дешёвый поиск по первичному ключу из кэша, ошибка оценки почти не стреляет. Больно, когда внутренняя сторона дорогая — полный проход или тяжёлый поиск на каждую строку снаружи.

Для Go-сервиса практическое правило: после массового импорта в той же джобе делай ANALYZE таблицы, не жди autovacuum. Если ошибка оценки из-за связанных колонок (город и индекс всегда ходят вместе) — помогает CREATE STATISTICS по этим колонкам.

Рычаг 5: память

Hash  Buckets: 262144  Batches: 4  Memory Usage: 6928kB      -- 500 000 заказов, work_mem = 4MB

Batches: 4 значит, что хэш-таблица не влезла в work_mem (по умолчанию 4 МБ) и была разрезана на 4 куска через диск. С work_mem = '256MB' на стенде стало Batches: 1 и вдвое быстрее. Можно поднять память для одного тяжёлого запроса:

err := pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
    if _, err := tx.Exec(ctx, `SET LOCAL work_mem = '256MB'`); err != nil { // только этой транзакции
        return err
    }
    rows, err := tx.Query(ctx, reportSQL)
    // ...
})

SET LOCAL, а не SET — ровно по причине из урока 0012: иначе настройка утечёт на соединение в пуле. И не поднимай work_mem глобально «на всякий случай»: он выделяется на каждую операцию сортировки или хэша в каждом соединении, 100 соединений × несколько операций × 256 МБ — и сервер упал по памяти.

Когда рычаги кончились: менять задачу

  • Тяжёлый отчёт по многим таблицам, который не обязан быть до секунды свежим, — материализованное представление (MATERIALIZED VIEW) с периодическим REFRESH, или денормализованная колонка.
  • Аналитика по миллиардам строк — это уже не к PostgreSQL, а к колоночной базе (урок 0007).
  • На стороне Go: N+1 — это тоже «медленный JOIN», только размазанный по сети. 1000 запросов в цикле меняются на один JOIN или на один запрос WHERE order_id = ANY($1) с массивом id и сборку в map в коде.

Частая ошибка на собесе

Начать с «добавлю индексы». Сильный ответ начинается с «посмотрю EXPLAIN ANALYZE»: без плана непонятно, какой индекс нужен и нужен ли он вообще. Каждый индекс замедляет запись.

«JOIN медленный, лучше переписать на подзапрос». Для PostgreSQL JOIN и эквивалентный подзапрос часто дают один и тот же план. Ускоряет не синтаксис, а то, сколько строк и каким алгоритмом обрабатывается. Исключение, которое стоит назвать, — EXISTS вместо JOIN + DISTINCT.

«Внешний ключ даёт индекс». В PostgreSQL — нет. Индекс на FK-колонку создают руками.

«Подскажу планировщику, какой JOIN использовать». В PostgreSQL нет хинтов (без расширений). Планировщику не приказывают, а дают ему верную статистику и подходящие индексы.

Смотреть только на EXPLAIN без ANALYZE. Там одни оценки. Главная находка — расхождение оценки и факта — видна только с ANALYZE.

Формулировка для собеса: «Сначала смотрю EXPLAIN (ANALYZE, BUFFERS): какой алгоритм выбран — Nested Loop, Hash или Merge, — где расходятся оценка и факт по строкам и где большие Seq Scan или уход на диск. Дальше по ситуации. Самое частое — индекс на ключ соединения: PostgreSQL не создаёт его для внешнего ключа сам. Дальше — уменьшить вход: фильтр раньше, только нужные колонки, агрегация до соединения, EXISTS вместо JOIN с DISTINCT. Проверяю, что условие соединения без функций и с одинаковыми типами, иначе индекс не работает. Если оценка строк врёт — ANALYZE. Если хэш или сортировка уходят на диск — SET LOCAL work_mem для конкретного запроса. А для тяжёлых отчётов — материализованное представление.»
