SELECT FOR UPDATE на Read Committed: что делает и когда нужен

Одна победа этого урока: глядя на метод сервиса, ты за минуту решаешь, нужен ли в нём FOR UPDATE, и можешь объяснить, что именно он вернёт на Read Committed, когда строка занята другой транзакцией.

Продолжение урока «Read Committed». Там разобрано, что уровень не защищает от потерянного обновления. Здесь — главный инструмент против него. Примеры про PostgreSQL, про MySQL отдельная врезка в конце.

Аналогия

Обычный SELECT — это подойти к общей доске и сфотографировать запись. Фотографируют все одновременно, никто никому не мешает. Но пока ты идёшь считать по фото, запись на доске уже могут стереть и написать заново.

SELECT ... FOR UPDATE — это повесить на запись табличку «занято, правлю я». Смотреть на доску по-прежнему можно (обычным SELECT), а вот тот, кто тоже хочет править эту запись, встаёт в очередь и ждёт, пока ты не снимешь табличку. Табличка снимается сама в конце твоей транзакции (COMMIT или ROLLBACK).

Формально

FOR UPDATE — блокировка строк на уровне строки. Строки, которые вернул запрос, блокируются до конца транзакции. Другие транзакции, которые хотят их UPDATE, DELETE или тоже взять FOR UPDATE, ждут. Обычные SELECT без блокировки не ждут никогда (это работа MVCC).

Отсюда главное отличие от простого SELECT: он читает «снимок», а FOR UPDATE читает актуальное зафиксированное состояние строки и держит его неизменным, пока ты не закончишь.

Что происходит на Read Committed

Склад, остаток 5. Две транзакции пытаются взять его на резерв.

ШагТранзакция AТранзакция B
1BEGIN;BEGIN;
2SELECT qty FROM stock WHERE id=1 FOR UPDATE; → 5, строка заблокирована
3тот же запрос с FOR UPDATE → стоит и ждёт
4UPDATE stock SET qty = 0 WHERE id=1; COMMIT;
5просыпается и получает 0, а не 5

Шаг 5 — суть урока. Пока B ждала, строка изменилась. На Read Committed PostgreSQL после ожидания перечитывает свежую версию строки и заново проверяет условие WHERE. Поэтому B увидит 0 и решит в коде «резервировать нечего». Без блокировки B получила бы устаревшее 5 из своего снимка и продала бы товар второй раз.

Что ещё делает перепроверка:

  • Если после чужого изменения строка перестала подходить под WHERE (например, WHERE status='new', а её уже перевели в 'paid'), она из результата пропадает. Запрос вернёт на одну строку меньше.
  • Если строку удалили, она тоже пропадает.
  • Ошибки нет. Это отличие от Repeatable Read (ниже).

Чем отличается от Repeatable Read

Read CommittedRepeatable Read
Что видит обычный SELECTсвежий снимок на каждый запросодин снимок на всю транзакцию
FOR UPDATE, строка изменена и закоммичена, пока ждалиперечитывает свежую версию и продолжаетошибка 40001 could not serialize access, нужен retry
Нужен retry-циклобычно нет (кроме deadlock)да

Поэтому на Read Committed FOR UPDATE — самый простой способ безопасного read-modify-write: не нужны ни повторы транзакции, ни Serializable.

Код: где ставить блокировку

func (s *Service) Reserve(ctx context.Context, sku string, n int) error {
    return s.store.WithTx(ctx, pgx.ReadCommitted, func(tx pgx.Tx) error {
        var qty int
        // 1. Блокируем первым делом, до любых других чтений этой строки
        err := tx.QueryRow(ctx,
            `SELECT qty FROM stock WHERE sku = $1 FOR UPDATE`, sku).Scan(&qty)
        if err != nil {
            return err // pgx.ErrNoRows: товара нет
        }
        // 2. Решение в коде. Это безопасно: никто не изменит строку до COMMIT
        if qty < n {
            return ErrNotEnough
        }
        // 3. Запись
        _, err = tx.Exec(ctx, `UPDATE stock SET qty = qty - $1 WHERE sku = $2`, n, sku)
        return err
    })
}

Порядок важен. Если сначала прочитать остаток обычным SELECT, а FOR UPDATE взять потом, то первое значение уже может быть устаревшим. Блокировка должна идти до чтения, на котором ты строишь решение.

Когда FOR UPDATE уместен

СитуацияПочему
Читаешь строку, проверяешь в Go сложные правила (лимиты, статус, курс), потом пишешьУсловие не свернуть в один UPDATE ... WHERE
Меняешь несколько связанных строк по единой логике (перевод между счетами)Нужен согласованный взгляд на обе строки до записи
Конечный автомат статусов, где переход зависит от истории или позиций заказаСтатус не должен меняться под ногами, пока считаешь
Очередь задач: несколько воркеров берут по однойFOR UPDATE SKIP LOCKED — занятые строки пропускаются, воркеры не ждут друг друга
Нужно выстроить в очередь операции над дочерними строкамиБлокируешь родителя (rooms, users) — все дочерние операции идут по одной

Когда FOR UPDATE не нужен или не поможет

СитуацияЧто вместо
Проверку и запись можно сделать одним запросомUPDATE stock SET qty = qty - $1 WHERE sku = $2 AND qty >= $1. Быстрее и без явной блокировки
Только читаешьОбычный SELECT. Блокировка зря создаст очередь
Инвариант про набор строк или их отсутствие (нет пересекающейся брони, «хотя бы один дежурный»)FOR UPDATE не блокирует строки, которых ещё нет. Нужен constraint (UNIQUE, EXCLUDE), Serializable с retry или блокировка родителя
Транзакция длинная, внутри вызовы внешних сервисовБлокировка висит всё это время. Выноси сетевые вызовы за пределы транзакции
Одна очень «горячая» строка (счётчик, который обновляют тысячи раз в секунду)Очередь на блокировке съест пропускную способность. Шардировать счётчик или считать асинхронно

Опасности FOR UPDATE

  • Deadlock (взаимная блокировка). A держит строку 1 и ждёт строку 2, B держит 2 и ждёт 1. PostgreSQL сам убьёт одну из транзакций с ошибкой 40P01. Лекарство: всегда блокировать строки в одном порядке (ORDER BY id) и уметь повторить транзакцию.
  • JOIN блокирует все таблицы. SELECT ... FROM orders o JOIN users u ... FOR UPDATE заблокирует строки и заказов, и пользователей. Ограничь: FOR UPDATE OF o.
  • ORDER BY и LIMIT. После ожидания строки могут пропасть из результата или прийти в другом порядке, поэтому LIMIT 1 может вернуть пусто, хотя подходящая строка была. Для очередей это решают SKIP LOCKED в связке с условием.
  • Блокировка есть только внутри транзакции. Без BEGIN (в autocommit) она снимется сразу после запроса, и ты защитил ровно ничего.

Варианты блокировки строки

ВариантЧто делает
FOR UPDATEСамая сильная: блокирует UPDATE, DELETE и другие блокировки строки
FOR NO KEY UPDATEСлабее: не мешает вставкам в дочерние таблицы с внешним ключом на эту строку. Подходит, если ключ строки ты не меняешь
FOR SHAREДругие могут читать с такой же блокировкой, но менять строку нельзя. «Убедись, что не изменят»
NOWAITНе ждать, сразу вернуть ошибку, если строка занята
SKIP LOCKEDЗанятые строки молча пропустить (очереди воркеров)

Пессимистичная и оптимистичная блокировка

FOR UPDATE — это пессимистичная блокировка: «сначала займу, потом работаю, конфликтов не будет». Альтернатива — оптимистичная: не блокировать, а при записи проверить, что строку никто не менял.

UPDATE orders SET status = $1, version = version + 1
WHERE id = $2 AND version = $3;   -- 0 строк: кто-то успел раньше, перечитай и повтори

Пессимистичную берут, когда конфликты часты и повторять дорого. Оптимистичную — когда конфликты редки (правки карточки в админке) и не хочется держать строку заблокированной, пока пользователь думает.

Врезка про MySQL InnoDB

В теории из банка вопросов (mysql/concurency.md) SELECT ... FOR UPDATE — явная блокировка строк, которую ставит и обычный UPDATE. Там же совет: если используешь блокирующее чтение, попробуй уровень READ COMMITTED. Причина в том, что InnoDB на Repeatable Read ставит ещё и блокировки интервалов между индексными записями (gap locks), из-за чего растёт число взаимных блокировок. На Read Committed их почти нет. В PostgreSQL gap-блокировок нет, там этот совет неактуален.

Частая ошибка на собесе

Сказать «FOR UPDATE защищает от фантомов». Нет: он блокирует только существующие строки, которые вернул запрос. Вставить новую строку под то же условие всё равно можно.

Ставить FOR UPDATE «на всякий случай» везде. Так получают очереди и deadlock. Сначала пробуют атомарный UPDATE ... WHERE или ограничение в БД.

Читать строку без блокировки, а блокировать потом. Решение принято на устаревших данных.

Формулировка для собеса: «FOR UPDATE блокирует выбранные строки до конца транзакции: другие транзакции не смогут их изменить и будут ждать. На Read Committed после ожидания PostgreSQL перечитывает свежую версию строки и заново проверяет условие, так что я принимаю решение по актуальным данным и без ошибок сериализации, в отличие от Repeatable Read. Я беру его, когда решение принимается в коде на основе прочитанной строки. Если проверку и запись можно сделать одним UPDATE ... WHERE, блокировка не нужна. Блокирую в одном порядке, чтобы не было deadlock, и не держу транзакцию долго.»
