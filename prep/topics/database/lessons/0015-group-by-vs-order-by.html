GROUP BY и ORDER BY: один схлопывает, другой переставляет

Одна победа этого урока: ты задаёшь себе один вопрос — «после этого изменится число строк?» — и сразу знаешь, что нужно. Меняется (была тысяча продаж, стало четыре клиента) — это GROUP BY. Не меняется, просто другой порядок — ORDER BY. И главное следствие: GROUP BY ничего не сортирует.

Вопросы банка: «Что такое GROUP BY?», «Что такое ORDER BY?», «Каков порядок логического выполнения SQL-запроса?», «Чем WHERE отличается от HAVING?». Все примеры ниже сняты с живого PostgreSQL 16 — их можно повторить руками в практике к уроку.

Аналогия

На столе куча чеков за неделю.

  • ORDER BY — разложить чеки по сумме, от большего к меньшему. Все чеки на месте, каждый виден, просто лежат в другом порядке.
  • GROUP BY — разложить чеки по конвертам, по конверту на покупателя, и на каждом конверте написать итог: «3 чека, 2100 ₽». Дальше ты работаешь с конвертами. Отдельный чек уже не видно — только то, что написано на конверте.

И ещё: конверты после раскладки лежат как попало. Если нужен порядок конвертов — их надо отдельно отсортировать. Это и есть GROUP BY + ORDER BY вместе.

Аналогия для Go: результат GROUP BY без ORDER BY похож на обход map через range — все ключи на месте, но порядок никто не обещал.

Пример: 10 продаж

ORDER BY — 10 строк было, 10 и осталось:

SELECT * FROM sales ORDER BY amount DESC;
--  id | customer | category | amount
--   2 | Боря     | техника  |   3000
--   8 | Вика     | техника  |   2500
--   9 | Боря     | одежда   |   1500
--  ... ещё 7 строк
-- (10 rows)

GROUP BY — 10 продаж схлопнулись в 4 клиента:

SELECT customer, count(*) AS cnt, sum(amount) AS total
FROM sales
GROUP BY customer;
--  customer | cnt | total
--  Аня      |   3 |  2100
--  Вика     |   3 |  3600
--  Боря     |   3 |  5200
--  Гоша     |   1 |   900
-- (4 rows)

Посмотри на порядок: Аня, Вика, Боря, Гоша. Не по алфавиту, не по сумме. Это не ошибка — так работает группировка через хэш-таблицу (в плане HashAggregate, тот же «хэш», что в Hash Join из урока 0014). Порядок групп ничем не гарантирован.

Правило колонок в GROUP BY

После группировки на каждого клиента одна строка. Если попросить ещё и category — какую из трёх категорий Ани показать? База не угадывает, а падает:

SELECT customer, category, sum(amount) FROM sales GROUP BY customer;
-- ERROR:  column "sales.category" must appear in the GROUP BY clause
--         or be used in an aggregate function

Правило: каждая колонка в SELECT либо есть в GROUP BY, либо внутри агрегата. Хочешь категорию — добавь её в группировку (GROUP BY customer, category, групп станет больше) или агрегируй (string_agg(category, ', '), max(category)).

Исключение, которое отличает уверенный ответ: если группировать по первичному ключу, PostgreSQL разрешает остальные колонки этой таблицы без агрегата — они однозначно определяются ключом. SELECT id, customer, amount FROM sales GROUP BY id работает.

Вместе: сначала конверты, потом порядок

Самый частый реальный запрос — «топ клиентов по выручке»:

SELECT customer, sum(amount) AS total
FROM sales
GROUP BY customer          -- 10 продаж → 4 клиента
ORDER BY total DESC        -- 4 клиента по убыванию суммы
LIMIT 2;                   -- первые два
--  customer | total
--  Боря     |  5200
--  Вика     |  3600

Здесь видно, почему порядок шагов важен. ORDER BY выполняется после SELECT, поэтому в нём доступен алиас total. А WHERE выполняется до группировки и до SELECT — там никакого total ещё нет:

SELECT customer, sum(amount) AS total FROM sales WHERE total > 2000 GROUP BY customer;
-- ERROR:  column "total" does not exist

-- фильтр по группам - это HAVING, он после GROUP BY
SELECT customer, sum(amount) AS total
FROM sales
GROUP BY customer
HAVING sum(amount) > 2000
ORDER BY total DESC;
--  Боря 5200 / Вика 3600 / Аня 2100

Цепочка для собеса: FROM → WHERE (строки) → GROUP BY (конверты) → HAVING (конверты) → SELECT → ORDER BY → LIMIT.

И ещё следствие из того же порядка: после GROUP BY в ORDER BY тоже можно только колонки группировки и агрегаты. GROUP BY customer ORDER BY sold_on падает той же ошибкой — по какой дате сортировать конверт с тремя чеками?

Две тонкости ORDER BY, полезные в Go-сервисе

1. Одинаковые значения — порядок между ними не определён.

SELECT id, sold_on, amount FROM sales ORDER BY sold_on LIMIT 3;
--  2 | 2026-10-01 | 3000      ← сначала id 2
--  1 | 2026-10-01 |  500
--  3 | 2026-10-02 | 1200

У продаж 1 и 2 одна дата, и база вправе отдать их в любом порядке. Для пагинации это баг: на второй странице строка может повториться, а другая потеряться. Лечится уникальным «добивающим» полем:

SELECT id, sold_on, amount FROM sales ORDER BY sold_on, id LIMIT 3;
--  1 | 2026-10-01 |  500
--  2 | 2026-10-01 | 3000
--  3 | 2026-10-02 | 1200

2. NULL при сортировке. GROUP BY собирает все NULL в одну группу. А ORDER BY в PostgreSQL считает NULL больше любого значения: при ASC они в конце, при DESC — в начале. Управляется явно: ORDER BY category NULLS LAST.

И сам Go-код: порядок из базы сохраняется, только пока ты складываешь строки в слайс. Положишь в map — порядок пропадёт, как в аналогии выше.

rows, err := db.Query(ctx, `
    SELECT customer, sum(amount) AS total
    FROM sales
    GROUP BY customer
    ORDER BY total DESC, customer`)   // порядок задаёт SQL, тай-брейк по имени
// ...
var top []CustomerTotal               // слайс, а не map - порядок сохранится
for rows.Next() {
    var t CustomerTotal
    if err := rows.Scan(&t.Customer, &t.Total); err != nil {
        return nil, err
    }
    top = append(top, t)
}

Частая ошибка на собесе

«GROUP BY сортирует результат». Нет. В старом MySQL 5.x он действительно сортировал неявно, отсюда миф, но MySQL 8 и PostgreSQL этого не обещают. Нужен порядок — пиши ORDER BY.

«GROUP BY — это как DISTINCT». Похоже только на поверхности: GROUP BY без агрегатов действительно убирает дубли. Но смысл GROUP BY — посчитать что-то по группе.

Фильтровать агрегат в WHERE. WHERE sum(amount) > 2000 — ошибка: WHERE работает до группировки. Для групп — HAVING.

Пагинация по неуникальному полю. ORDER BY created_at LIMIT 20 OFFSET 20 без id в конце — дубли и пропуски между страницами.

Формулировка для собеса: «GROUP BY схлопывает строки в группы — одна строка на группу — и нужен, чтобы посчитать агрегаты: count, sum, avg. В SELECT после него можно только колонки группировки и агрегаты. ORDER BY число строк не меняет, только упорядочивает, и выполняется почти последним — поэтому в нём доступны алиасы из SELECT. GROUP BY порядок не гарантирует, так что если он нужен — добавляю ORDER BY, а для пагинации ещё и уникальный тай-брейк вроде id. Фильтр по строкам — WHERE, по группам — HAVING.»
Хочешь увидеть всё это руками? Практика к уроку: 10 строк, семь шагов «введи → предскажи → проверь», загрузка меньше секунды.
