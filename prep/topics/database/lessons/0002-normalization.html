Нормализация: зачем резать одну таблицу на много

Одна победа этого урока: дав тебе одну "плохую" таблицу, ты найдёшь в ней конкретный баг (аномалию), скажешь, какая нормальная форма его чинит, и разложишь таблицу на несколько правильных.

Аналогия

Представь один Excel-файл на всю компанию, где в одной вкладке намешано всё: и данные заказа, и имя с почтой клиента, и название с ценой товара, — просто потому что "так проще, всё в одном месте". Проблема вылезает не сразу: она вылезает, когда почту клиента меняют в одной строке, а в десяти других — забывают.

Нормализация — это правила, по которым такой файл режут на несколько вкладок (таблиц): отдельно клиенты, отдельно товары, отдельно заказы, — связанных между собой через id. Это буквально обратная операция тому, что делает JOIN: нормализация раскладывает данные по разным таблицам, а JOIN потом собирает их обратно для конкретного запроса.

Формальное определение: что чинит каждая форма

Сначала — три поломки, к которым приводит "один файл на всё" (аномалии). Дальше — нормальные формы, каждая следующая чинит свою поломку поверх предыдущей.

АномалияВ чём проблема
Insert (вставки)Нельзя добавить факт (например, нового клиента), пока не появился связанный с ним факт (его первый заказ)
Update (обновления)Один и тот же факт продублирован в нескольких строках — обновив одну, легко забыть остальные, и данные рассинхронизируются
Delete (удаления)Удаляя одну строку (например, последний заказ клиента), случайно стираешь и факт, который с этим заказом вообще не связан по смыслу (контакты клиента)
ФормаУсловие
1NFКаждая ячейка — одно неделимое значение (никаких списков через запятую в одном поле), нет повторяющихся групп колонок
2NF1NF + при составном первичном ключе каждое неключевое поле зависит от всего ключа, а не от его части
3NF2NF + неключевое поле зависит только от первичного ключа напрямую, а не через другое неключевое поле (нет "транзитивных" зависимостей)
BCNFУсиленная 3NF: для любой зависимости X → Y слева обязан стоять суперключ (встречается редко, в основном на собесе как "а слышал ли ты про неё")

Сквозной пример

Одна таблица orders_flat, где в каждой строке — заказ вместе с данными клиента и товара:

orders_flat
order_id (PK)customer_namecustomer_emailproduct_nameproduct_pricequantity
1Аняana@mail.comКлавиатура20001
2Аняana@mail.comМышь5002
3Борисboris@mail.comКлавиатура20001

Первичный ключ тут один столбец — order_id — значит 1NF и 2NF формально не нарушены (2NF вообще не про эту таблицу, ей нужен составной ключ, пример ниже). А вот 3NF нарушена дважды, и именно отсюда растут все три аномалии:

  • order_id → customer_name → customer_email — email зависит не от order_id напрямую, а через имя клиента.
  • order_id → product_name → product_price — цена зависит не от order_id напрямую, а через название товара.

Аномалии на живых данных:

  • Update anomaly: Аня меняет почту на anna@mail.com. Если обновить только строку 1, в строке 2 останется старый ana@mail.com — теперь у "одного и того же" клиента два разных email в базе.
  • Delete anomaly: Аня отменяет оба своих заказа (строки 1 и 2 удаляются) — вместе с ними исчезает единственное место, где вообще хранился её email. Клиент "потерялся", хотя удаляли-то заказы, а не клиента.
  • Insert anomaly: появился новый клиент Вика, которая пока ничего не заказала. Вставить её некуда — в этой таблице клиент существует только как часть строки заказа, а заказа ещё нет.

Раскладываем до 3NF

CREATE TABLE customers (
  id    SERIAL PRIMARY KEY,
  name  TEXT,
  email TEXT
);

CREATE TABLE products (
  id    SERIAL PRIMARY KEY,
  name  TEXT,
  price NUMERIC
);

CREATE TABLE orders (
  id          SERIAL PRIMARY KEY,
  customer_id INT REFERENCES customers(id),
  product_id  INT REFERENCES products(id),
  quantity    INT
);

Теперь email хранится один раз на клиента, цена — один раз на товар. Обновление email — один UPDATE в одной строке. Удаление всех заказов Ани не трогает таблицу customers. Новый клиент без заказов просто вставляется в customers отдельной строкой. Три аномалии исчезли — но теперь, чтобы показать "заказ с именем клиента и названием товара", нужен JOIN трёх таблиц (см. предыдущий урок).

Отдельно про 2NF: нужен составной ключ

2NF не про таблицу выше — там ключ из одного столбца. Она про ситуацию вроде order_items(order_id, product_id, product_name, quantity) с составным первичным ключом (order_id, product_id). Если в такой таблице лежит ещё и product_name — он зависит только от половины ключа (product_id), а не от пары целиком. Это и есть нарушение 2NF: неключевое поле "прилипло" не ко всему ключу, а к его части.

Частая ошибка на собесе. Отвечать так, будто "нормализация — это всегда хорошо, чем выше форма, тем лучше". На реальных высоконагруженных системах сознательно денормализуют: например, хранят author_name прямо в таблице comments, чтобы не делать JOIN с users на каждый запрос ленты, или держат готовый счётчик likes_count вместо COUNT(*) на лету. Это осознанный компромисс "скорость чтения вместо чистоты схемы", а не незнание нормализации — и на собесе стоит показать, что ты понимаешь обе стороны, а не только "нормализуй всё до 3NF".
