FOR UPDATE против UPDATE — шпаргалка

Суть: обычный UPDATE тоже блокирует строку до конца транзакции. Выбор не «с блокировкой или без», а где решение: в SQL или в коде на Go.

Одинаково

  • Берут блокировку уровня строки и держат до COMMIT / ROLLBACK.
  • Ждут, если строку занял другой.
  • На Read Committed после ожидания перечитывают свежую версию и заново проверяют WHERE.
  • На Repeatable Read в этой ситуации — ошибка 40001.
  • Обычным SELECT не мешают.

Ловушки

  • 0 затронутых строк не говорит о причине: строки нет или условие не выполнено.
  • FOR UPDATE перед UPDATE той же строки без решения между ними — лишний round-trip.
  • UPDATE ... WHERE id IN (1,2) встречными транзакциями — риск deadlock 40P01 из непредсказуемого порядка.
  • FOR UPDATE строже обычного UPDATE: мешает вставке дочерних строк по внешнему ключу.
Формулировка для собеса: «Обычный UPDATE сам блокирует строку до конца транзакции, поэтому одиночный UPDATE ... WHERE уже атомарен — особенно когда новое значение считается из текущего в SQL. FOR UPDATE беру, когда решение принимается в коде между чтением и записью. Нужно значение обратно — UPDATE ... RETURNING. Потерянное обновление даёт не UPDATE, а чтение без блокировки перед ним.»
