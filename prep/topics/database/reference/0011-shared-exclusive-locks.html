Shared и exclusive lock — шпаргалка

Суть: это sync.RWMutex для строк. S = RLock (много читателей, никто не меняет), X = Lock (один, никто больше). Держатся до конца транзакции.

Совместимость

Хочу ↓		SX
S✅⏳
X⏳⏳

Совместимы только две S.

В SQL

PostgreSQLMySQL InnoDB
SFOR SHAREFOR SHARE / LOCK IN SHARE MODE
XFOR UPDATEFOR UPDATE
Берут X самиUPDATE, DELETEUPDATE, DELETE

PostgreSQL дробит S/X на 4 режима: FOR KEY SHARE < FOR SHARE < FOR NO KEY UPDATE < FOR UPDATE.

MVCC

  • Обычный SELECT блокировок строк не берёт и никого не ждёт — читает снимок.
  • Ждут только блокирующие операции: FOR SHARE, FOR UPDATE, UPDATE, DELETE.
  • Исключение: InnoDB на Serializable превращает обычный SELECT в FOR SHARE.
  • Учебниковый вариант «читатель берёт S» — это изоляция на блокировках, не MVCC.

Когда что

ЗадачаБлокировка
Строка не должна измениться, пока делаю что-то рядом (родитель → потомок)FOR SHARE
Собираюсь менять эту строкуFOR UPDATE сразу
Просто прочитатьничего, обычный SELECT

Ловушки

  • FOR SHARE, затем UPDATE той же строки параллельно — deadlock 40P01.
  • «Shared запрещает другим читать» — нет, разрешает читать и брать S.
  • «Exclusive блокирует любые чтения» — не при MVCC.
  • Гранулярность отдельно от режима: строка или таблица. ALTER TABLE берёт сильнейшую табличную блокировку.
  • Intention locks (IS/IX) в InnoDB — табличная пометка, что внутри держат S/X на строках.
Формулировка для собеса: «Shared — много транзакций одновременно, никто не меняет. Exclusive — одна, несовместима ни с чем. Держатся до конца транзакции. В PostgreSQL это FOR SHARE и FOR UPDATE, UPDATE берёт X сам. Из-за MVCC обычный SELECT блокировок не берёт и не ждёт. Как RLock и Lock в sync.RWMutex.»
