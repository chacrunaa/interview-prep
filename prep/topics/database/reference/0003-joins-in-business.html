JOIN под задачу — шпаргалка

Два вопроса выбирают JOIN: 1) про кого строка в результате — та таблица главная; 2) нужны ли записи без пары — да значит LEFT, нет значит INNER.

Бизнес-формулировкаЧто брать
«…по каждому клиенту, включая тех, кто не покупал»LEFT JOIN + COUNT(o.id) + COALESCE(SUM, 0)
«только те, кто ни разу не…»LEFT JOIN + WHERE o.id IS NULL, либо NOT EXISTS
«выручка по менеджерам за месяц»INNER JOIN — нет факта, нет строки
«сверь наш каталог с прайсом поставщика»FULL OUTER JOIN, либо EXCEPT для одной стороны
«дашборд со всеми месяцами, включая пустые»CROSS JOIN с календарём + LEFT JOIN фактов
«сотрудник и его руководитель»self-join через два алиаса, LEFT (у главного нет руководителя)

Опасности — по убыванию важности

ОпасностьКак проявляетсяЧто делать
Размножение строк (fan-out)Связь один-ко-многим дублирует левую строку; SUM и COUNT завышаются. Заказ 500 ₽ с 3 позициями даёт 1500 ₽Агрегировать до соединения — подзапросом или CTE. SUM(DISTINCT) не спасает
LEFT стал INNERУсловие по правой таблице в WHERE отсекает NULL-строки, записи без пары исчезаютПереносить условие в ON
COUNT(*) при LEFT JOINДаёт 1 вместо 0 — строка-то существует, просто с NULLСчитать COUNT(o.id)
Забытое условиеДекартово произведение N × M кладёт базуПроверять, что у каждого JOIN есть ON
Индекс не работаетСоединение колонок разных типов; функция над колонкой в ONПриводить типы в схеме, не оборачивать ключ в функцию
N+1 в коде1000 клиентов = 1001 запрос из ORMОдин JOIN, но помнить про fan-out и схлопывать в коде

Физические алгоритмы (для вопроса «как JOIN выполняется»)

АлгоритмКогдаРиск
Nested LoopЛевая таблица мелкая, справа индекс по ключуБез индекса — полный перебор
Hash JoinБольшие объёмы, соединение по =Не влезло в память — слив на диск
Merge JoinОбе стороны отсортированы по ключуНет сортировки — придётся сортировать
Формулировка для собеса: «Главный риск JOIN — не скорость, а корректность: связь один-ко-многим размножает строки и агрегаты начинают врать. Поэтому агрегирую до соединения, а условия по правой таблице в LEFT JOIN держу в ON, а не в WHERE.»
