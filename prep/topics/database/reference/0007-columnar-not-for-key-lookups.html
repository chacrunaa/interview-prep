Колоночные базы — шпаргалка

Суть: колоночная база хранит каждую колонку отдельно. Читает только нужные столбцы, отлично сжимает, мгновенно добавляет колонки. Строки целиком в ней нет — её собирают. Критерий выбора не объём данных, а форма запросов.

Почему плохо по ключу

  • Разреженный индекс: засечка на гранулу (тысячи строк), а не на строку. «Одна строчка» = прочитать много лишнего.
  • Сборка строки: N колонок — N чтений с диска и N распаковок. SELECT * — худший случай.
  • Нет транзакций, точечных UPDATE/DELETE, оконных функций, полноценного оптимизатора.
  • Уникальности нет: ReplacingMergeTree дедуплицирует асинхронно, сразу после вставки видны дубли.

Вместе (CQRS)

Go ──запись──► PostgreSQL        (транзакции, FOR UPDATE)
   └─событие──► Kafka ─► ClickHouse (отчёты, дашборды)

Цена: задержка согласованности. Отчёты — ок, «покажи мой только что созданный заказ» — не ок.

Ошибки на собесе

  • «Данных много — значит ClickHouse». Объём не критерий.
  • «Колоночная быстрее везде». Быстрее на агрегациях, медленнее на строке целиком.
  • «ClickHouse — NoSQL». Реляционный, с SQL, просто без транзакций.
  • Назвать выгоду без механизма: сжимает — потому что в колонке однотипные значения; читает мало — потому что лишние колонки не трогает.
Формулировка для собеса: «Колоночная хранит колонки отдельно: читает только нужные столбцы и хорошо сжимает — выигрыш на агрегациях. Но строки целиком нет, индекс разреженный по гранулам, транзакций и точечных UPDATE нет. Если запросы известны и идут по ключу, строчная база с индексом дешевле. Продуктовое — в PostgreSQL, события и агрегаты — в ClickHouse, то есть CQRS ценой задержки согласованности.»
