MVCC в PostgreSQL — шпаргалка

Суть: строка хранится в нескольких версиях. UPDATE = пометить старую xmax + вставить новую с xmin. Транзакция по своему снимку решает, какую версию видеть. Читатели не ждут писателей.

Кирпичики

ЧтоСмысл
tupleфизическая версия строки, адрес — ctid
xminтранзакция, создавшая версию
xmaxтранзакция, удалившая или заменившая версию (0 — никто)
snapshotкакие транзакции для меня уже закоммичены
SELECT xmin, xmax, ctid, * FROM acc;

Правило видимости

  1. xmin закоммичена для моего снимка (или это я).
  2. xmax пуст, откатилась или ещё не закоммичена для моего снимка.

Читатель ↔ писатель: не ждут. Писатель ↔ писатель: ждут блокировку строки.

VACUUM

  • Мёртвые версии копятся → bloat таблиц и индексов.
  • VACUUM убирает версии, не видимые ни одному снимку; место переиспользуется, файл не уменьшается.
  • Autovacuum не выключать. VACUUM FULL сжимает, но блокирует таблицу.
  • Долгая/забытая транзакция блокирует уборку во всей базе.
  • HOT-update: не меняются индексированные колонки + есть место в странице → индексы не трогаются.
  • Wraparound: 32-битные номера транзакций, VACUUM «замораживает» старые версии.

В Go

  • pgx.BeginFunc или defer tx.Rollback(ctx) сразу после Begin.
  • Никаких HTTP-вызовов и ожиданий внутри транзакции.
  • Страховка в базе: idle_in_transaction_session_timeout.

RC — снимок на запрос, RR — на транзакцию. Мёртвые версии убирает autovacuum, но долгая транзакция ему мешает во всей базе. В InnoDB старые версии в undo-логе.»
