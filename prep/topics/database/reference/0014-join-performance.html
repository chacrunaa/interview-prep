Ускорение JOIN — шпаргалка

Суть: сначала EXPLAIN (ANALYZE, BUFFERS), потом рычаг под конкретную беду. Цепочка: статистика → оценка строк → выбор алгоритма.

Алгоритмы

ХорошБолит
Nested Loopснаружи мало, внутри индекснет индекса; оценка снаружи занижена
Hash Joinмного строк, =не влез в work_mem
Merge Joinобе стороны отсортированыбольшая сортировка

Что искать в плане → рычаг

СимптомРычаг
Seq Scan по большой таблице ради малого числа строкиндекс на ключ соединения (FK сам не индексируется), составной / INCLUDE
Оценка rows ≪ actualANALYZE, CREATE STATISTICS
Внутренний узел с огромным loopsто же: статистика или индекс
Batches: N>1, external merge Diskменьше колонок/строк; SET LOCAL work_mem
Индекс есть, но не используетсяубрать функцию и приведение типа из ON; индекс по выражению
JOIN + DISTINCT ради проверки наличияEXISTS

Меньше входа

  • Фильтр как можно раньше, без SELECT *.
  • Агрегировать до соединения (и fan-out лечится).
  • Hash/Merge — только для равенства; диапазон в ON = Nested Loop.

Код

CREATE INDEX CONCURRENTLY ON order_items (order_id);
ANALYZE imports;                       -- после массовой загрузки
SET LOCAL work_mem = '256MB';          -- в транзакции тяжёлого запроса

Дальше рычагов

  • Материализованное представление / денормализация для отчётов.
  • Аналитика по миллиардам строк — колоночная БД.
  • N+1 в Go → один JOIN или WHERE id = ANY($1).

Ловушки

  • Начинать с «добавлю индексы» без плана.
  • «Подзапрос быстрее JOIN» — план часто одинаковый.
  • FK не создаёт индекс в PostgreSQL.
  • Хинтов в PostgreSQL нет.
  • EXPLAIN без ANALYZE — только оценки.
  • Глобальный work_mem × операции × соединения = OOM.
Формулировка для собеса: «Смотрю EXPLAIN ANALYZE: алгоритм, расхождение оценки и факта, Seq Scan, уход на диск. Чаще всего — индекс на ключ соединения, FK его не создаёт. Потом уменьшаю вход: фильтры, колонки, агрегация до JOIN, EXISTS. Условие без функций и с одинаковыми типами. Врёт оценка — ANALYZE. Диск — SET LOCAL work_mem. Тяжёлые отчёты — материализованное представление.»
