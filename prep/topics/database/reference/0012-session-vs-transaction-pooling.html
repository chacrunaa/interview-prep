Session и transaction pooling — шпаргалка

Суть: режим пула — это на сколько PgBouncer отдаёт клиенту настоящее соединение. В transaction mode — до COMMIT, поэтому состояние сессии живёт не дольше транзакции: иначе пропадает у тебя или утекает к чужому клиенту.

Режимы

РежимЗакреплениеОграниченияЭкономия
Sessionдо отключения клиентанетслабая, с pgxpool почти нулевая
Transactionдо COMMIT/ROLLBACKнет сессионного состояниясильная, стандарт для Go
Statementна один запроснет транзакций из нескольких запросовмаксимальная, редко

Что ломается в transaction mode

ЧтоЗамена
SET ...SET LOCAL / set_config(..., true) в транзакции
pg_advisory_lockpg_advisory_xact_lock
LISTENпрямое соединение к PostgreSQL
Временные таблицы между транзакциямиON COMMIT DROP в одной транзакции
PREPARE в SQL, курсоры WITH HOLDне использовать
Кэш prepared statements в pgxPgBouncer 1.21+ с max_prepared_statements или QueryExecModeExec

Всё внутри одной транзакции работает как обычно.

В Go

// плохо: разные соединения, SET утечёт чужим (даже без PgBouncer)
pool.Exec(ctx, `SET search_path = t42`); pool.Query(ctx, `SELECT ...`)

// хорошо
pgx.BeginFunc(ctx, pool, func(tx pgx.Tx) error {
    tx.Exec(ctx, `SELECT set_config('search_path', $1, true)`, schema)
    ...
})

// pgx через старый PgBouncer
cfg.ConnConfig.DefaultQueryExecMode = pgx.QueryExecModeExec

В проде

  • Сервис → PgBouncer (transaction).
  • Миграции, LISTEN, сессионные advisory-блокировки → напрямую в PostgreSQL, второй DSN.
  • pgxpool (внутри процесса) и PgBouncer (между процессами и базой) — разные пулы, стоят друг за другом.

Ловушки

  • «В transaction mode нельзя транзакции» — наоборот, они целиком на одном соединении.
  • «Без PgBouncer SET отдельным запросом безопасен» — нет, pgxpool тоже раздаёт соединения.
  • Ошибки prepared statement "stmtcache_..." does not exist — кэш pgx и старый PgBouncer.
Формулировка для собеса: «Session — соединение за клиентом до отключения, работает всё, экономии мало. Transaction — соединение на одну транзакцию, экономия большая, но сессионное состояние теряется или утекает: SET, advisory lock, LISTEN, temp-таблицы, prepared statements. Держу состояние внутри транзакции (SET LOCAL, xact-блокировки), миграции и LISTEN — напрямую в базу.»
