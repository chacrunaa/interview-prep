Виды связей — шпаргалка

Суть: все связи — один механизм, внешний ключ на стороне «много». Вид связи задают: где лежит FK и какие ограничения на нём.

Четыре случая

СвязьТаблицКак
1:N2user_id bigint NOT NULL REFERENCES users(id) в дочерней
1:12то же + UNIQUE, либо user_id PRIMARY KEY REFERENCES users(id)
N:M3связующая: два FK + PRIMARY KEY (a_id, b_id), два JOIN
Иерархия1parent_id bigint REFERENCES categories(id), self-join

Many-to-One — не отдельный вид, это 1:N со стороны ребёнка (в банке тут опечатка). Говори: три вида + самоссылка.

Индексы

  • Автоиндекс только у PRIMARY KEY и UNIQUE. FOREIGN KEY индекса не создаёт → CREATE INDEX ON orders (user_id);
  • Без него страдает и JOIN, и DELETE родителя (проверка детей перебором).
  • Составной PK работает слева направо: для обратного направления CREATE INDEX ON order_items (product_id);

Ошибки на собесе

  • N:M между двумя таблицами — негде хранить FK.
  • 1:1 без UNIQUE — это 1:N.
  • «Many-to-One — отдельный вид» — нет.
  • «FK создаёт индекс» — нет.
  • «FK нужен для JOIN» — нет, для целостности и каскадов.
  • Связующая без составного PK — молча копит дубли пар.
  • FK на естественный ключ (email, ИНН) — смена значения тянет каскадное обновление всех детей. Ссылайся на суррогатный id.
  • Про «кластерный индекс у PRIMARY KEY» — это MySQL/SQL Server, не PostgreSQL.
Формулировка для собеса: «Три вида связей, все через внешний ключ на стороне "много". 1:N — FK в дочерней. 1:1 — тот же FK плюс UNIQUE, чище — когда FK сам первичный ключ. N:M напрямую не выразить, нужна связующая таблица с составным PK из двух FK, туда же кладутся атрибуты связи. Плюс самоссылка для иерархии. Обязательность — NOT NULL на FK. Внешний ключ нужен не для JOIN, а для целостности и каскадов, и индекс на него создаётся руками.»
