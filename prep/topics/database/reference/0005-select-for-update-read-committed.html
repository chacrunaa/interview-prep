FOR UPDATE на Read Committed — шпаргалка

Суть: блокирует выбранные строки до конца транзакции. Другие UPDATE, DELETE и FOR UPDATE на этих строках ждут. Обычные SELECT не ждут.

Поведение на Read Committed (PostgreSQL)

  • Строка занята — ждёшь коммита или отката владельца.
  • После ожидания строка перечитывается, условие WHERE проверяется заново.
  • Строка перестала подходить или удалена — пропадает из результата. Ошибки нет.
  • На Repeatable Read в этой же ситуации ошибка 40001 и нужен retry.

Нужен ли FOR UPDATE?

СитуацияРешение
Проверку и запись можно уместить в один UPDATE ... WHEREОн, без блокировки
Читаю строку, решаю в Go, пишуFOR UPDATE, до любых других чтений этой строки
Несколько связанных строк, единая логикаFOR UPDATE, порядок ORDER BY id
Очередь задач, много воркеровFOR UPDATE SKIP LOCKED
Инвариант про набор или отсутствие строкConstraint, Serializable + retry или блокировка родителя. FOR UPDATE не блокирует несуществующие строки
Только чтениеОбычный SELECT
Конфликты редки, пользователь «думает» над формойОптимистичная: WHERE version = $n

Варианты

ВариантСмысл
FOR UPDATEСильнейшая блокировка строки
FOR NO KEY UPDATEНе мешает вставкам в дочерние таблицы по внешнему ключу
FOR SHAREЧитать с гарантией «не изменят», параллельный FOR SHARE можно
NOWAITНе ждать, ошибка сразу
SKIP LOCKEDПропустить занятые строки
OF таблицаПри JOIN блокировать строки только этой таблицы

Ловушки

  • Без BEGIN блокировка снимается сразу после запроса.
  • Deadlock: блокировать в одном порядке, держать retry на 40P01.
  • Не держать транзакцию долго, никаких внешних вызовов внутри.
  • С ORDER BY и LIMIT после ожидания результат может быть короче или в другом порядке.
  • Сначала блокировка, потом чтение, иначе решение принято на устаревшем значении.
  • MySQL InnoDB: на Repeatable Read блокирующее чтение ставит gap locks, отсюда совет использовать Read Committed.
Формулировка для собеса: «FOR UPDATE блокирует строки до конца транзакции. На Read Committed после ожидания строка перечитывается, и я решаю по актуальным данным без ошибок сериализации. Беру его, когда решение принимается в коде по прочитанной строке; если хватает атомарного UPDATE ... WHERE, блокировка не нужна. Порядок блокировок фиксированный, транзакция короткая.»
