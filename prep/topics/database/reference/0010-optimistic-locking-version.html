Optimistic locking и ошибка сериализации — шпаргалка

Суть: оптимистичная блокировка ничего не блокирует — это проверка version при записи. Конфликт версии замечает приложение (0 строк), ошибку сериализации — база (40001).

Реализация

-- читаем без блокировки
SELECT id, address, version FROM orders WHERE id = $1;      -- version = 7
-- пишем с проверкой и инкрементом
UPDATE orders SET address = $2, version = version + 1
WHERE id = $1 AND version = $3;                               -- $3 = 7
-- RowsAffected() == 0  →  ErrVersionConflict (или строку удалили)

Конфликт версии против 40001

Когда повторять

СигналДействие
40001, 40P01 (deadlock)Вся транзакция с BEGIN, включая чтения. Лимит попыток, пауза с jitter
Конфликт версии, версию принёс пользовательНе повторять. 409 Conflict (или 412 при If-Match), показать свежие данные
Конфликт версии, цикл внутри сервисаПовторить «прочитал — решил — записал». Были другие записи по прочитанному — вся транзакция

СитуацияЧем

Ловушки

  • Проверка версии в Go, а не в WHERE того же UPDATE — гонка.
  • Нет version = version + 1 — следующие не узнают о записи.
  • При 40001 повторять только упавший запрос — транзакция мертва, решения устарели.
  • Автоповтор конфликта из пользовательской формы — тихое затирание чужой правки.
  • Письма и Kafka внутри повторяемой функции — дубли. Побочки после коммита или через outbox.
  • Версия на Repeatable Read: изменение после начала транзакции даёт 40001, а не 0 строк — обрабатывать оба.
Формулировка для собеса: «Optimistic locking — поле version: UPDATE ... SET ..., version = version + 1 WHERE id = $1 AND version = $2, 0 строк — конфликт, его видит приложение и решает по смыслу: 409 пользователю или повтор. 40001 возвращает сама база на Repeatable Read и Serializable, транзакция после него мертва, и повторяется вся транзакция с начала.»
