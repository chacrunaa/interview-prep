Практика: сам ломаешь и чинишь JOIN

Шесть шагов на живом PostgreSQL. В каждом ты вводишь команду, сначала предсказываешь, что покажет план, и только потом открываешь ответ. Цель — научиться видеть в EXPLAIN ANALYZE пять рычагов из урока.

Все планы в ответах получены на этом же стенде (PostgreSQL 16). Миллисекунды у тебя будут другие — важны форма плана и во сколько раз меняется время. Урок: «Как ускорить JOIN».

Подготовка (один раз)

Нужен только Docker. Отдельный одноразовый контейнер, твои базы он не трогает:

docker run -d --name join-lab -e POSTGRES_PASSWORD=lab \
  -v ~/personal/interview-prep/prep/topics/database/labs:/lab:ro \
  postgres:16.6-alpine

docker exec -it join-lab psql -U postgres

Дальше всё в psql:

\i /lab/0014-join-performance.sql
\timing on
SET max_parallel_workers_per_gather = 0;

Последняя строка выключает параллельные воркеры, чтобы планы были короче и читались как в уроке. Без неё сверху появятся Gather и Parallel Seq Scan — суть та же, просто таблицу читают три процесса вместо одного.

Что лежит в базе: customers — 100 000, orders — 500 000 (у нечётных клиентов по 10 заказов, у чётных ни одного), order_items — 2 000 000 (по 4 на заказ), products — 1000, imports — 1000.

Шаг 1. Внешний ключ без индекса

EXPLAIN (ANALYZE)
SELECT o.id, i.sku, i.qty
FROM orders o
JOIN order_items i ON i.order_id = o.id
WHERE o.customer_id = 43;

Предскажи: у клиента 43 всего 10 заказов, 40 позиций. Сколько строк order_items прочитает база, чтобы их найти? Какой будет алгоритм соединения?

Что должно получиться 
Hash Join  (actual time=0.129..146.551 rows=40 loops=1)
  Hash Cond: (i.order_id = o.id)
  ->  Seq Scan on order_items i  (actual rows=2000000 loops=1)     ← все 2 млн
  ->  Hash  ... Batches: 1  Memory Usage: 9kB
        ->  Bitmap Heap Scan on orders o  (actual rows=10 loops=1)
              ->  Bitmap Index Scan on orders_customer_id_idx
Execution Time: 146.601 ms

Чтобы найти 40 строк, прочитано 2 000 000. По orders база ищет индексом (10 строк), складывает их в маленькую хэш-таблицу (9 kB) и прогоняет через неё всю order_items. Другого выхода у неё нет: по order_id нет индекса, хотя внешний ключ есть.

Проверь сам: \d order_items — в списке индексов только order_items_pkey. Внешний ключ в PostgreSQL индекс не создаёт.

Шаг 2. Добавляем индекс

CREATE INDEX order_items_order_id_idx ON order_items (order_id);

И снова запрос из шага 1 (стрелка вверх в psql).

Предскажи: останется ли Hash Join? Сколько раз (loops) выполнится поиск по order_items?

Что должно получиться 
Nested Loop  (actual time=0.036..0.349 rows=40 loops=1)
  ->  Bitmap Heap Scan on orders o  (actual rows=10 loops=1)
        ->  Bitmap Index Scan on orders_customer_id_idx
  ->  Index Scan using order_items_order_id_idx on order_items i
        (actual rows=4 loops=10)                                   ← 10 заглядываний по 4 строки
Execution Time: 0.424 ms

146 мс → 0.4 мс, примерно в 350 раз. Ты не просил базу сменить алгоритм — планировщик сам решил, что 10 быстрых заглядываний по индексу дешевле одного полного прохода. loops=10 — по разу на каждый заказ снаружи.

На живой базе индекс создают CREATE INDEX CONCURRENTLY, чтобы не блокировать запись. Здесь можно без него.

Шаг 2б. Индекс есть — а база его не берёт

EXPLAIN (ANALYZE)
SELECT o.id, i.sku, i.qty
FROM orders o
JOIN order_items i ON i.order_id = o.id
WHERE o.customer_id < 20000;

Предскажи: индекс order_items_order_id_idx теперь есть. Будет ли Nested Loop с ним?

Что должно получиться 
Hash Join  (actual time=20.181..206.712 rows=400000 loops=1)
  ->  Seq Scan on order_items i  (actual rows=2000000 loops=1)
  ->  Hash  Buckets: 131072  Batches: 1  Memory Usage: 4540kB
        ->  Bitmap Heap Scan on orders o  (actual rows=100000 loops=1)
Execution Time: 214.104 ms

Нет — и это правильно. Снаружи 100 000 заказов, нужна пятая часть всех позиций. 100 000 заглядываний в индекс — это 100 000 прыжков по случайным страницам, а один последовательный проход быстрее. Это вопрос банка «Когда полное сканирование выгоднее доступа по индексу?»: когда запрос возвращает значительную часть строк.

Вывод для собеса: индекс — не приказ, а возможность. Планировщик берёт его, только если по оценке так дешевле.

Шаг 3. Устаревшая статистика

Имитируем массовый импорт: статистика по imports собрана, когда там была 1000 строк со статусом done. Теперь заливаем 100 000 строк со статусом new — autovacuum на этой таблице выключен, так что статистику никто не обновит.

INSERT INTO imports (sku, status)
SELECT 'SKU-' || (g % 1000), 'new' FROM generate_series(1, 100000) g;

EXPLAIN (ANALYZE)
SELECT count(*)
FROM imports im
JOIN products p ON p.sku = im.sku
WHERE im.status = 'new';

Предскажи: сколько строк со статусом new ожидает планировщик (rows= в оценке)? Какой алгоритм он выберет, если поверит своей оценке? Запрос будет думать секунд 5–10 — это и есть ответ.

Что должно получиться 
Aggregate  (actual time=6938.683..6938.693 rows=1 loops=1)
  ->  Nested Loop  (cost=0.00..1553.29 rows=1) (actual rows=100000 loops=1)
        Join Filter: (im.sku = p.sku)
        Rows Removed by Join Filter: 99900000
        ->  Seq Scan on imports im  (cost=... rows=1) (actual rows=100000 loops=1)
              Filter: (status = 'new'::text)
        ->  Seq Scan on products p  (actual rows=1000 loops=100000)
Execution Time: 6939.241 ms

Планировщик ждал rows=1: в последней статистике значения new не было вовсе. Под одну строку Nested Loop — идеальный выбор: «один раз пройду 1000 товаров». А пришло 100 000, и products перечитана 100 000 раз (loops=100000) — почти 100 миллионов лишних сравнений (Rows Removed by Join Filter).

Теперь почини:

ANALYZE imports;
-- и тот же EXPLAIN (ANALYZE) ещё раз
Aggregate  (actual time=17.465..17.466 rows=1 loops=1)
  ->  Hash Join  (rows=100010) (actual rows=100000 loops=1)
        Hash Cond: (im.sku = p.sku)
        ->  Seq Scan on imports im  (rows=100010) (actual rows=100000)
        ->  Hash  Batches: 1  Memory Usage: 47kB
              ->  Seq Scan on products p  (actual rows=1000 loops=1)
Execution Time: 17.501 ms

Оценка совпала с фактом → Hash Join → 6.9 секунды превратились в 17 мс, в 400 раз. Ни индексов, ни переписывания запроса: одна команда ANALYZE.

Тонкость, которую я нашёл, пока готовил стенд: если внутри Nested Loop дешёвый поиск по первичному ключу, ошибка оценки почти не стреляет — сотни тысяч заглядываний в индекс из кэша проходят быстро. Больно становится, когда внутренняя сторона дорогая, как здесь: полный проход без индекса на каждую строку снаружи.

Шаг 4. Хэш не влез в память

SET work_mem = '4MB';   -- значение по умолчанию, на всякий случай

EXPLAIN (ANALYZE)
SELECT o.customer_id, sum(i.qty)
FROM orders o
JOIN order_items i ON i.order_id = o.id
GROUP BY o.customer_id;

Предскажи: хэш-таблица строится по 500 000 заказов. Найди в плане узел Hash — что написано в Batches?

Что должно получиться 
HashAggregate  (actual time=985.347..988.468 rows=50000 loops=1)
  ->  Hash Join  (actual time=109.046..797.150 rows=2000000 loops=1)
        ->  ...
        ->  Hash  Buckets: 262144  Batches: 4  Memory Usage: 6928kB    ← 4 куска через диск
Execution Time: 993.241 ms

Batches: 4 — хэш-таблица не поместилась в work_mem, и база разрезала соединение на 4 прохода с временными файлами на диске. Теперь дай памяти:

SET work_mem = '256MB';
-- тот же EXPLAIN (ANALYZE)
  ->  Hash Join  (actual time=67.738..371.888 rows=2000000 loops=1)
        ->  Hash  Buckets: 524288  Batches: 1  Memory Usage: 23628kB  ← всё в памяти
Execution Time: 596.878 ms

Batches: 1, время почти вдвое меньше. В psql обычный SET безопасен — это одна твоя сессия. В Go-сервисе с пулом соединений — только SET LOCAL внутри транзакции (урок 0012).

Верни как было: RESET work_mem;

Шаг 5. Приведение типа в ON

EXPLAIN (ANALYZE)
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.customer_id = 43;

EXPLAIN (ANALYZE)
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id::text = o.customer_id::text
WHERE o.customer_id = 43;

Предскажи: запросы логически одинаковые. Будет ли во втором использован первичный ключ customers_pkey?

Что должно получиться 
-- первый
Nested Loop  (actual time=0.151..0.505 rows=10 loops=1)
  ->  Index Scan using customers_pkey on customers c  (actual rows=1 loops=1)
  ->  Bitmap Heap Scan on orders o  (actual rows=10 loops=1)
Execution Time: 0.627 ms

-- второй
Hash Join  (rows=5000) (actual time=0.122..32.434 rows=10 loops=1)
  ->  Seq Scan on customers c  (actual rows=100000 loops=1)       ← индекс не использован
  ->  Hash  ->  Bitmap Heap Scan on orders o  (actual rows=10 loops=1)
Execution Time: 32.523 ms

Индекс построен по id, а не по id::text. Как только над колонкой появилась функция или приведение, база не может искать по индексу и читает все 100 000 клиентов. Заодно сломалась оценка: ждёт 5000 строк вместо 10.

В жизни это случается, когда в двух таблицах ключ хранится в разных типах (int и varchar). Лечение — одинаковые типы в схеме или индекс по выражению.

Шаг 6. EXISTS против JOIN + DISTINCT

EXPLAIN (ANALYZE)
SELECT DISTINCT c.id, c.name
FROM customers c
JOIN orders o ON o.customer_id = c.id;

EXPLAIN (ANALYZE)
SELECT c.id, c.name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

Предскажи: оба возвращают 50 000 клиентов с заказами. Сколько строк выйдет из JOIN в первом запросе до DISTINCT?

Что должно получиться 
-- JOIN + DISTINCT
HashAggregate  (actual rows=50000)                      ← схлопнули обратно
  Group Key: c.id, c.name
  ->  Hash Join  (actual rows=500000)                   ← размножили до 500 000
        ->  Seq Scan on orders o  (actual rows=500000)
        ->  Hash  ->  Seq Scan on customers c  (actual rows=100000)
Execution Time: 225.391 ms

-- EXISTS
Hash Join  (actual rows=50000)
  ->  Seq Scan on customers c  (actual rows=100000)
  ->  Hash
        ->  HashAggregate  (actual rows=50000)          ← сначала уникальные customer_id
              Group Key: o.customer_id
              ->  Seq Scan on orders o  (actual rows=500000)
Execution Time: 87.753 ms

Первый запрос сначала размножил каждого клиента на все его 10 заказов (500 000 строк), а потом DISTINCT схлопнул их, сравнивая id и name. Это fan-out из урока 0003, только замаскированный.

С EXISTS планировщику понятно, что заказы нужны только как «есть или нет». Он сначала собрал 50 000 уникальных customer_id, а потом соединил. В 2.5 раза быстрее, и запрос честнее говорит, что ты хочешь.
