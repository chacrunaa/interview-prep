Что такое highload и как его определять

Одна победа этого урока: на вопрос «а это вообще highload?» ты отвечаешь не числом RPS, а тем, что сломалось бы в простом решении и по какой оси, и умеешь привести примеры из реальных классов систем.

Опирается на банк: architecture/topic_07_highload_caching.md (счётчики лайков и просмотров с записью «миллионы RPS», главная маркетплейса с 50 000 RPS на один ключ, лента новостей и её гибридная стратегия), golang/topic_10_frameworks.md (где Highload оправдан: прокси-серверы, анти-фрод, рекламные RTB), devops/topic_09_opentelemetry_jaeger.md (на 100 000 RPS сохранять все трейсы невозможно). Честно про пробел: определения highload и порогов в банке нет. Определение и «ориентиры по порядку» ниже собраны из общей практики и условны: у разных компаний планка разная. Своё место на этой шкале смотри в prep/sd/load-my-projects.md.

Аналогия

Маленькое кафе: один повар, одна касса, 20 столиков. Если придёт вдвое больше людей, купишь плиту побольше, и всё. Теперь вокзальный фудкорт: тысячи людей в час, десятки точек. Плитой побольше не обойтись, нужно менять устройство кухни: несколько линий, заготовки заранее, отдельные очереди на заказ и выдачу.

Highload — это не «много народу». Это когда простое устройство перестаёт работать, и приходится придумывать другое.

Определение

Highload (высоконагруженная система) — система, в которой простое решение (один сервер, одна база, синхронная обработка, одна запись на событие) перестаёт справляться хотя бы по одной оси нагрузки, и поэтому приходится проектировать масштабирование: батчи, очереди, кеши, шардирование, специальные хранилища.

Нет единого порога «выше 10 000 RPS — highload». Порог зависит от стоимости запроса, объёма данных и требований к задержке (урок 0003). Один и тот же RPS может быть тривиальным для кеша и тяжёлым для записи в базу.

Обрати внимание на последний пример: RPS API у него всего ~600, но проект всё равно высоконагруженный, потому что ломается запись и объём.

Как определить: шесть вопросов

  1. Что сломается, если сделать самое простое решение? Одна база, одна запись на событие, синхронная обработка. Главный вопрос.
  2. Какой ресурс упрётся первым: CPU, память, диск, сеть, база, внешний API?
  3. Растут ли данные быстрее, чем влезают на один узел? Сколько в сутки, сколько хранить.
  4. Есть ли жёсткий бюджет задержки на хвосте (p95/p99, сквозная задержка)?
  5. Нужно ли масштабироваться горизонтально: несколько инстансов, партиции, шарды?
  6. Что дорого стоит: простой, потеря события, дубль?

Если на вопрос 1 ты можешь привести конкретную поломку и что сделал — это сильное доказательство. Если не можешь, система скорее обычная.

Доказательство «простое ломается»: батчи вместо вставки на событие

Пример из твоей практики: ClickHouse и ошибка «Too many parts». Каждая вставка создаёт кусок данных на диске, и если вставок слишком много, фоновые слияния не успевают. При 28 000 точек/с вставка на каждую точку даёт ~28 000 вставок в секунду. Решение — копить и писать пачками по размеру или по времени:

func batcher(in <-chan Point, flush func([]Point), size int, every time.Duration) {
    buf := make([]Point, 0, size)
    t := time.NewTicker(every)
    defer t.Stop()
    for {
        select {
        case p, ok := <-in:
            if !ok {
                if len(buf) > 0 {
                    flush(buf)
                }
                return
            }
            buf = append(buf, p)
            if len(buf) >= size {
                flush(buf)
                buf = make([]Point, 0, size) // не переиспользуем: flush может держать срез
            }
        case <-t.C:
            if len(buf) > 0 {
                flush(buf)
                buf = make([]Point, 0, size)
            }
        }
    }
}

Арифметика: 28 000 точек/с с размером батча 14 000 даёт всего ~2 вставки в секунду вместо 28 000. Период every нужен, чтобы редкие данные не залёживались в буфере. Цена — задержка до одной секунды-другой между точкой и записью, и она должна укладываться в бюджет сквозной задержки.

Как ответить вслух

«Я определяю highload не по RPS, а по тому, ломается ли простое решение. На моём проекте поток шёл около 28 тысяч точек в секунду, на пике 50 тысяч, то есть около 2,4 миллиарда в сутки. Простая схема «вставка на точку в обычную базу» не работала, поэтому мы писали пачками в ClickHouse и разделили синхронный API и асинхронную обработку. API при этом всего около 600 RPS, но запросы тяжёлые из-за fan-out в аналитику. То есть система высоконагруженная по записи и объёму, а не по числу запросов».

Если спросят «а выше ли это 100 000 RPS?» — нет, и это нормально: честно называть масштаб лучше, чем спорить о ярлыке.

Частая ошибка на собесе

  • Определять highload одним числом RPS. «Больше 10k — highload» — формальный ответ, который ломается на первом уточнении.
  • Называть highload всё подряд. 5 000 RPS на кешируемых GET — не highload, а на запись — может быть.
  • Не уметь привести поломку простого решения. Без неё слово «highload» ничем не подкреплено.
  • Путать высокую нагрузку с высокой сложностью. Много микросервисов и Kafka не делают систему highload сами по себе.
  • Забыть про запись и объём. Highload бывает и при малом RPS.
  • Завышать масштаб. Интервьюер из крупной компании легко проверит порядок величин.
Если что-то из этого осталось непонятным — просто спроси, разберём отдельно.
