Сложности деплоя микросервисов

Одна победа этого урока: ты называешь главную причину сложности — во время выката две версии живут одновременно — и показываешь, как с ней справляются в базе данных, в API и в самом процессе выката.

Опирается на банк: architecture/topic_01_monolith_microservices.md (Shared Database, распределённый монолит, Strangler Fig), database/topic_10_migrations_liquibase.md (Expand-Contract), devops/topic_03_kubernetes.md (стратегии обновления Deployment, Helm, пробы, откат), devops/topic_07_sre_metrics.md (Error Budget). Честно про пробел: готового ответа «какие сложности у деплоя микросервисов» в банке нет, урок собран из этих кусков. Blue-green, graceful shutdown, совместимость API и схем событий в банке не описаны: эти части помечены «вне банка», сверяй с документацией.

Аналогия

Представь, что ты меняешь экипаж и оборудование на идущем поезде. Остановить поезд нельзя, поэтому по вагону заменяют по одному. Какое-то время часть вагонов старые, часть новые, и они должны сцепляться между собой. Любое изменение, из-за которого новый вагон не сцепляется со старым, остановит поезд.

В монолите деплой — это одна замена целиком. В микросервисах таких поездов десятки, они сцеплены друг с другом через API, очереди и базы, и меняют их независимо и в разное время. Вся сложность из этого и вытекает.

Главная идея: одновременно живут две версии

При обычном выкате (rolling) старые поды заменяются новыми постепенно. На протяжении минут одновременно работают:

  • старая и новая версия этого же сервиса;
  • разные версии соседних сервисов, которые вызывают друг друга и читают чужие события;
  • одна общая база под обеими версиями.

Поэтому любое изменение должно быть обратно совместимым с тем, что ещё работает. Ниже по слоям.

1. База данных

Банк прямо называет причину: «старая и новая версии бэкенда работают одновременно, поэтому удаление или переименование колонки одним шагом сломает работающие инстансы». Решение — Expand-Contract, схема меняется в несколько релизов:

  1. Expand: добавили новую колонку phone_number (NULLABLE), старую phone не трогаем.
  2. Dual write: новая версия пишет в обе колонки.
  3. Backfill: фоновый скрипт батчами переносит старые данные.
  4. Переключение чтения: приложение читает из новой колонки.
  5. Contract: старую колонку удаляют отдельной миграцией, когда её уже никто не использует.

Побочная выгода: пока схема совместима с обеими версиями, откат кода безопасен. Откатить код назад легко, а откатить данные (rollback в Liquibase) бывает невозможно, если новая версия уже что-то записала.

Общая база — отдельная беда. По банку, при Shared Database сервис A не может переименовать колонку, потому что это сломает сервис B: исчезает независимый цикл релизов, получается «распределённый монолит». Правило Database-per-Service: доступ к чужим данным только через API или события.

2. Контракты между сервисами (вне банка)

  • API. Новое поле добавляют, старое не удаляют и не меняют смысл, пока на нём сидит хоть один клиент. Ломающие изменения идут в новую версию контракта (/v2, новый proto-пакет), а старая живёт, пока потребители не переехали. В банке упомянут «строго версионированный REST/gRPC контракт» для публичного API.
  • События и очереди. В топике Kafka одновременно лежат сообщения старой и новой схемы. Новый консьюмер должен уметь прочитать старые сообщения (они лежат по retention), а старый консьюмер — не падать на незнакомых полях нового формата.
  • Порядок выката. Если для релиза нужно «сначала задеплоить B, потом A, и всё одной связкой», это признак того, что сервисы связаны слишком сильно. В банке это называется распределённый монолит: мнимая независимость без независимого релиза.

Откат. В Kubernetes Deployment умеет откат к предыдущей версии, у Helm — helm rollback. Но откат сработает, только если схема БД и контракты остались совместимы: иначе возвращённая старая версия упадёт на новых данных.

4. Сам процесс: как под «умирает» и «рождается»

  • Пробы (из банка). Под принимает трафик только когда readiness-проба проходит, а liveness перезапускает зависший. Плохая проба — типичная причина того, что новая версия выкатилась «зелёной», а трафик уже идёт в неготовый под. Для диагностики CrashLoopBackOff банк советует kubectl describe pod, kubectl logs, проверку проб и конфигурации.
  • Graceful shutdown (вне банка). При замене Kubernetes шлёт поду SIGTERM. Если сервис просто завершится, оборвутся запросы в полёте. Правильно: перестать отвечать «готов» на readiness, дать балансировщику убрать под из пула, дообработать текущие запросы и выйти.
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM)
defer stop()

var ready atomic.Bool
mux.HandleFunc("/ready", func(w http.ResponseWriter, _ *http.Request) {
    if !ready.Load() { w.WriteHeader(http.StatusServiceUnavailable); return }
    w.WriteHeader(http.StatusOK)
})
srv := &http.Server{Addr: ":8080", Handler: mux}
go srv.ListenAndServe()
ready.Store(true)

<-ctx.Done()               // пришёл SIGTERM
ready.Store(false)          // readiness теперь 503: новые запросы не пойдут
time.Sleep(5 * time.Second) // дать балансировщику убрать под
shCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
defer cancel()
srv.Shutdown(shCtx)         // дожидается текущих запросов

Срок на всё это в Kubernetes ограничен terminationGracePeriodSeconds: после него под убьют принудительно, поэтому таймауты выше должны в него укладываться.

Связь с Kafka (урок 0002 по Kafka). Каждый перезапуск консьюмера запускает ребаланс группы. При выкате десятка подов подряд это каскад. Помогают кооперативный ребаланс и статичное членство, а при остановке нужно закоммитить offset до отзыва партиций.

5. Организационные сложности

  • Много конвейеров. Банк: независимый деплой каждого сервиса через CI/CD и Kubernetes. Сервисов десятки, у каждого свой пайплайн, свои конфиги и секреты. Это снимают шаблонами и Helm-чартами (helm install, upgrade, rollback — полное управление жизненным циклом).
  • Наблюдаемость. Чтобы canary и откат имели смысл, нужны метрики и трейсинг: без них непонятно, что новая версия сломана и в каком из сервисов. Банк для сложных цепочек вызовов отдельно называет распределённый трейсинг.
  • Скорость против надёжности: Error Budget. Если SLO 99,9%, бюджет ошибок — 0,1%. Пока он не потрачен, команда может выкатывать смелее. Когда бюджет исчерпан, наступает Feature Freeze: релизы новых функций останавливают, команда чинит надёжность. Банк в постмортеме предлагает и технические ограждения: canary-деплой и автоматический откат.
  • Переход с монолита. Strangler Fig по банку: перед монолитом ставят API Gateway, выносят один домен в новый сервис с собственной БД, синхронизируют данные (CDC / события) и переключают маршруты сначала через feature flag или canary на 5–10% пользователей.

Как ответить вслух

«Главная сложность в том, что при выкате одновременно живут две версии, а сервисов много и они выкатываются независимо. Поэтому всё должно быть обратно совместимо. В БД это Expand-Contract: сначала добавляем, потом переключаем, потом удаляем. В API и событиях добавляем, но не ломаем, ломающее идёт в новую версию. Сам выкат делаем rolling или canary с метриками и автооткатом, плюс readiness-пробы и graceful shutdown, чтобы не рвать запросы. Если сервисы приходится деплоить строго вместе, это распределённый монолит и признак общей БД или слишком тесных контрактов».

Частая ошибка на собесе

  • Перечислять только инструменты (Docker, Kubernetes, Helm) и не называть саму проблему совместимости версий.
  • «Просто откатим, если что». Откат кода без совместимой схемы БД и контрактов не работает. Откатить данные ещё сложнее.
  • Удалить или переименовать колонку одной миграцией. Это ломает работающие старые инстансы.
  • Считать canary и rolling одним и тем же. Rolling заменяет все поды по очереди и доходит до 100%. Canary держит новую версию на малой доле и ждёт решения по метрикам.
  • Забыть про graceful shutdown и пробы: «зелёный» деплой, а клиенты получают оборванные запросы.
  • Не отличать «независимый деплой» от «деплой по отдельности». Если порядок выката важен, независимости нет.
Если что-то из этого осталось непонятным — просто спроси, разберём отдельно.
