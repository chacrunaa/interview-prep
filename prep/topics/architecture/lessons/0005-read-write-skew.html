Перекос в чтение или запись

Одна победа этого урока: на вопрос «ваша система read-heavy или write-heavy?» ты отвечаешь про проект 2 (телеметрия бурения) за 30 секунд: в чём считал, куда перекос и какие решения из-за него приняли.

Продолжает уроки 0002 (уточнение «чтение или запись»), 0003 (стоимость запроса) и 0004 (что такое highload). Первоисточники: курс Балуна, тема 01.06 «Основные свойства ИС» (слайд 37, лекция 48:29) и тема 05.01 «Соцсеть: ключевое требование» — reference/balun-sd/map/course-map.md, на сайте курса 01.06 и 05.01 (сайт запускается через npm start). Цифры проекта — только из prep/sd/load-my-projects.md, пропуски ___ там тоже пропуски здесь. Честно про пробел: в банке вопросов InterviewPro нет отдельного разбора read/write ratio, есть только упоминание RWMutex «когда чтений намного больше, чем записей» в golang/topic_07_concurrency.md.

Аналогия

Библиотека и архив. В библиотеку книги привозят раз в месяц, а читают их каждый день сотни людей. Поэтому там всё сделано под читателя: каталог, копии популярных книг, книги на открытых полках. Расставлять новую книгу дольше — не страшно.

В архив, наоборот, каждый день привозят коробки документов, а заглядывают туда редко. Там всё сделано под приём: коробки ставят пачками в конец стеллажа, без каталога по каждой бумажке. Найти потом что-то дольше — не страшно.

Система с перекосом в чтение (read-heavy) — библиотека. С перекосом в запись (write-heavy) — архив. Нельзя сделать хранилище, идеальное для обоих сразу: что ускоряет одно, обычно замедляет другое.

Определение

Read / write ratio (соотношение чтений и записей) — во сколько раз операций чтения больше, чем операций записи, за одно и то же время. Курс Балуна относит его к базовым свойствам системы: от него напрямую зависят архитектура, способ хранения и выбор хранилища (тема 01.06, лекция 48:29).

  • Read-heavy: чтений намного больше. Типичный пример курса — соцсети: часто читают, редко пишут.
  • Write-heavy: записей намного больше. Пример курса — логи: часто пишут, редко читают. Телеметрия с датчиков — тот же случай.

В уроке 5 лектор называет это соотношение ключевым требованием (ASR — требование, без учёта которого архитектуру можно выбрасывать): соцсеть read-intensive, поэтому оптимизируем время ответа на чтение, даже если запись станет дороже. Это и есть смысл вопроса на собесе: перекос — это решение, которое ты принимаешь, а не просто цифра.

Главная ловушка: в чём считать

Соотношение имеет смысл, только если обе стороны посчитаны в одних единицах. Возьмём проект 2 из твоего файла:

ЧтоЗначениеЭто запись или чтение
Точек телеметрии~28 000/с, пик ~50 000/сзапись
Сообщений в брокере (со слов архитектора, сверить)~5 000/сзапись (те же точки пачками)
API, пик~600 RPSв основном чтение: дашборды и аналитика
Вставок в ClickHouse___/с, по ___ строкзапись
Строк, которые читает API___/с (600 × K × R из задачи 9)чтение

«28 000 к 600, значит 47 : 1» — так говорить нельзя: слева точки, справа HTTP-запросы. Один запрос дашборда может прочитать миллионы строк. Посчитай одну и ту же систему в разных единицах — и перекос может даже развернуться:

  • по числу событий (точка — событие записи, запрос — событие чтения): запись преобладает с большим отрывом;
  • по числу обращений к базе: вставок мало, потому что пишем батчами (___/с), а чтений 600 × K. Здесь может преобладать чтение;
  • по строкам или байтам: записываем ~28 000 строк/с, читаем 600 × K × R строк/с. Пока K и R не известны, ответа нет.

Поэтому честный ответ про проект 2 такой: «по входящему потоку система write-heavy; чтений по числу немного, но каждое тяжёлое». Ровно эта формулировка уже стоит в твоём файле в ёлочке «Чтение или запись?». Не надо придумывать одно красивое число.

Как это выглядело в проекте 2

Связываем каждое решение из файла с перекосом в запись:

  • ClickHouse — колоночное хранилище, рассчитанное на большие пачки вставок и аналитическое чтение. Сжатие ~12 раз (30 ТБ сырых → 2,5 ТБ) тоже работает на запись: меньше байт на диск.
  • Первым упёрлась запись: много мелких вставок давали ошибку «Too many parts». ClickHouse на каждую вставку создаёт новый кусок данных (part) и потом сливает куски в фоне; когда вставок слишком много, слияние не успевает.
  • Решение — батчи и буферизация: копим точки и пишем пачкой. Так 28 000 точек/с превращаются в ___ вставок/с.
  • Синхронный API отделён от асинхронной обработки: поток записи идёт через брокер и не мешает пользователям, которые читают дашборды.

Чтение в проекте тоже есть, и оно тяжёлое (fan-out из урока 0003). Это нормально: перекос по числу операций и стоимость отдельного запроса — две разные оси. Сильный ответ называет обе.

Код: батч-запись в Go

Главный приём write-heavy системы в миниатюре: копим точки и сбрасываем пачку, когда набралось size штук или прошло every времени — смотря что наступит раньше. Второе условие нужно, чтобы при слабом потоке точки не висели в буфере вечно.

type Point struct {
    SensorID uint32
    TS       time.Time
    Value    float64
}

// batcher копит точки и отдаёт их в flush пачками.
func batcher(ctx context.Context, in <-chan Point, size int, every time.Duration,
    flush func(context.Context, []Point) error) {

    buf := make([]Point, 0, size)
    tick := time.NewTicker(every)
    defer tick.Stop()

    send := func() {
        if len(buf) == 0 {
            return
        }
        if err := flush(ctx, buf); err != nil {
            log.Printf("flush %d points: %v", len(buf), err) // в проде: ретрай, а не потеря
        }
        buf = make([]Point, 0, size) // новый слайс: старый мог уйти в flush
    }

    for {
        select {
        case p, ok := <-in:
            if !ok {
                send()
                return
            }
            buf = append(buf, p)
            if len(buf) >= size {
                send()
            }
        case <-tick.C:
            send()
        case <-ctx.Done():
            send()
            return
        }
    }
}

Цена батча — задержка: точка может подождать до every, прежде чем попадёт в базу. Это часть сквозных p95 1,5 с «датчик → дашборд» из твоего паспорта. Такой обмен «чуть позже, но в разы дешевле» для write-heavy систем нормален.

Как ответить вслух

«Система write-heavy по входящему потоку: около 28 тысяч точек в секунду в среднем и до 50 тысяч на пике, это около 2,4 миллиарда точек в сутки. Чтение — дашборды и аналитика, около 600 RPS на пике. По числу запросов это немного, но каждый тяжёлый: на один дашборд приходится ___ обращений к ClickHouse. Поэтому дизайн шёл от записи: ClickHouse под пачки вставок, брокер между датчиками и базой, а первым упёрлась именно запись — ошибка «Too many parts» на мелких вставках, которую мы закрыли батчами и буферизацией. Если нужно точное соотношение, его надо считать в одних единицах: по строкам это ___ записи против ___ чтения в секунду».

Пропуски ___ — те же, что в load-my-projects.md. Пока их нет, говори «точную цифру не помню, порядок такой» — это лучше, чем выдуманное число.

Частая ошибка на собесе

  • Делить точки на HTTP-запросы. «28 000 к 600» — разные единицы. Сначала скажи, в чём считаешь.
  • Ответить «read-heavy» или «write-heavy» и замолчать. Вопрос задают ради следствий: что это поменяло в хранилище, кеше, очередях.
  • Путать перекос со стоимостью. Чтений может быть мало, а нагрузку от них большой. В проекте 2 так и есть.
  • Лечить write-heavy кешем. Кеш ускоряет чтение. Запись разгружают батчами, буфером, очередью и подходящим хранилищем.
  • Держать много индексов в write-heavy таблице. Каждый индекс платится на каждой вставке.
  • Не проговорить ASR. В курсе (урок 5) соотношение чтения и записи и есть ключевое требование, его называют до схемы.
Если что-то из этого осталось непонятным — просто спроси, разберём отдельно.
