Деплой микросервисов — шпаргалка

Суть: при выкате одновременно живут две версии (своего и соседних сервисов) на одной БД. Всё должно быть обратно совместимо.

По слоям

СлойПравило
БДExpand-Contract: добавить колонку (NULLABLE) → dual write → backfill батчами → читать из новой → удалить старую отдельной миграцией. Общая БД = распределённый монолит; нужен Database-per-Service.
API (вне банка)Поля добавлять, не удалять; ломающее — в новую версию контракта.
События (вне банка)В топике старые и новые сообщения вперемешку: новый консьюмер читает старые, старый не падает на новых полях.
Порядок выкатаЕсли нужен жёсткий порядок A→B, это признак связанности.

Стратегии выката

  • Recreate: удалить все старые, создать новые → простой.
  • RollingUpdate (по умолчанию): постепенно; maxSurge, maxUnavailable.
  • Canary: новая версия на малой доле, решение по метрикам.
  • Blue-green (вне банка): вторая полная среда, переключение трафика целиком.
  • Feature flag: выкатить выключенным, включать отдельно.
  • Откат: Deployment rollback, helm rollback; работает, только если схема БД и контракты совместимы.

Процесс пода

  • readiness — «можно слать трафик», liveness — «перезапусти меня». CrashLoopBackOff: describe, logs, пробы, конфиг.
  • Graceful shutdown (вне банка): SIGTERM → readiness 503 → пауза → http.Server.Shutdown в пределах terminationGracePeriodSeconds.
  • Консьюмеры Kafka: каждый рестарт = ребаланс; коммит offset до отзыва партиций.

Организация

  • Много пайплайнов → шаблоны и Helm.
  • Нужны метрики и трейсинг, иначе canary и откат слепые.
  • Error Budget = 100% − SLO; исчерпан → Feature Freeze. Ограждения: canary + автооткат.
  • Strangler Fig: API Gateway → вынести домен с собственной БД → CDC/события → feature flag/canary 5–10%.

Ловушки

  • Назвать только инструменты, а не проблему совместимости версий.
  • «Просто откатим» без совместимой схемы БД.
  • Rename/drop колонки одной миграцией.
  • Путать canary и rolling.
  • Не знать про graceful shutdown и пробы.
