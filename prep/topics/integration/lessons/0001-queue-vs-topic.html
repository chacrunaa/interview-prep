Очередь и топик: как в них пишут и как из них читают

Одна победа этого урока: на вопрос «чем очередь отличается от топика?» ты отвечаешь про запись и про чтение отдельно и в конце говоришь, что выбрать и почему.

Опирается на банк вопросов: integration/topic_04_rabbitmq_amqp.md (раздел «RabbitMQ против Apache Kafka», топология AMQP, ACK и prefetch) и integration/topic_03_apache_kafka.md (партиции, offset, consumer group, rebalancing, ключи).

Аналогия

  • Очередь — это стопка заданий на столе у бригады. Мастер берёт верхнее задание, делает, вычёркивает и выбрасывает. Если в бригаде три мастера, они делят стопку: каждое задание достаётся кому-то одному. Закончилась стопка — стол пуст. Прочитать вчерашнее задание нельзя: его уже выбросили.
  • Топик — это журнал в бухгалтерии, куда записи только дописывают в конец. Читатель никому ничего не «забирает»: он держит закладку («я дочитал до строки 1042») и листает свой экземпляр. У бухгалтерии и у аналитиков закладки свои, и друг другу они не мешают. Записи не пропадают после чтения — их убирают по сроку (например, через 7 дней). Хочешь перечитать неделю — сдвинул закладку назад.

Отсюда главное: очередь хранит «ещё не сделанную работу», топик хранит «историю событий».

Формально

RabbitMQ (протокол AMQP) — по формулировке банка, «Smart Broker, Dumb Consumer»: брокер сам следит за судьбой каждого сообщения и удаляет его после подтверждения (ACK).

Kafka — «Distributed Append-Only Commit Log», «Dumb Broker, Smart Consumer»: сообщения неизменяемы и лежат в журнале, а консьюмер сам управляет указателем на своё место — offset.

Путаница в словах. В RabbitMQ тоже есть слово «topic» — это Topic Exchange, тип обменника, который маршрутизирует по маске (audit.#). К топику Kafka он отношения не имеет: это правило раздачи, а не хранилище. Если интервьюер говорит «топик», уточни одной фразой, о чём речь.

Запись (producer)

RabbitMQ: пишем в обменник, а не в очередь

Продюсер никогда не кладёт сообщение прямо в очередь. Он отдаёт его в Exchange с routing_key, а обменник по правилам привязок (bindings) решает, в какие очереди скопировать сообщение. Может быть 0 очередей (сообщение отбросят или вернут при mandatory), одна или сто. Поэтому продюсер не знает, кто и сколько его читает.

producer ──(routing_key)──► Exchange ──┬──► Queue A ──► consumer 1
                                        └──► Queue B ──► consumer 2

Надёжность записи: Publisher Confirms — брокер присылает продюсеру ack, когда сообщение сохранено (для durable-очереди и persistent-сообщения — после записи на диск или репликации на кворум).

Kafka: пишем в топик, партиция выбирается по ключу

Продюсер пишет сразу в топик. Топик разбит на партиции — отдельные журналы, раскиданные по брокерам. Партицию выбирают так: есть ключ — hash(key) % numPartitions, то есть один ключ всегда попадает в одну партицию; нет ключа — по кругу (round-robin). Запись просто дописывается в конец партиции, ей присваивается offset — порядковый номер внутри партиции.

producer ──(key=user-7)──► Topic orders
                              ├─ partition 0: [0][1][2][3]...
                              ├─ partition 1: [0][1][2]...   ◄── user-7 всегда сюда
                              └─ partition 2: [0][1][2][3][4]...

Надёжность записи: параметр acks, репликация (лидер + реплики, ISR), идемпотентный продюсер enable.idempotence=true.

Чтение (consumer)

RabbitMQ: брокер толкает, ACK удаляет

  • Push. Брокер сам отправляет сообщения подписанному консьюмеру. Чтобы не залить его память, ставят prefetch — максимум неподтверждённых сообщений «в полёте».
  • Конкурирующие консьюмеры. Несколько воркеров на одну очередь делят её между собой: каждое сообщение достаётся одному. Хочешь больше скорости — добавляешь воркеров, лимита нет.
  • ACK = «готово, выбрасывай». После basic.ack сообщение удаляется навсегда. nack с requeue=true вернёт его в очередь, с requeue=false — выбросит или отправит в DLX (очередь «мёртвых писем»).
  • Одно сообщение — один получатель. Чтобы то же событие получили и биллинг, и аналитика, нужны две очереди, привязанные к одному обменнику (например, fanout). У каждой очереди свои копии.

Kafka: консьюмер тянет, offset двигает он сам

  • Pull. Консьюмер сам запрашивает пачку (poll) в своём темпе. Перегрузить его брокер не может.
  • Consumer group. Консьюмеры одного сервиса объединяются в группу (group.id), и партиции делятся между ними: одну партицию читает не больше одного консьюмера группы. Сообщения одной партиции идут строго по порядку.
  • Offset-коммит вместо ACK. Консьюмер записывает «дочитал до N» (commit). Сообщение при этом остаётся в топике — его удалит только retention (retention.ms / retention.bytes).
  • Много независимых читателей. Биллинг — одна группа, аналитика — другая. У каждой свои offset'ы, один и тот же топик читают обе, и никаких доп. очередей заводить не надо.
  • Replay. Сдвинул offset назад (или поднял новую группу с auto.offset.reset=earliest) — перечитал историю.
  • Потолок параллелизма — число партиций. 6 партиций и 10 консьюмеров в группе: 4 простаивают.

В коде на Go

// RabbitMQ (amqp091-go): пишем в обменник
err := ch.PublishWithContext(ctx, "orders", "orders.create", false, false,
    amqp.Publishing{DeliveryMode: amqp.Persistent, Body: body})

// читаем: ограничили «в полёте», подтверждаем руками
ch.Qos(10, 0, false)
msgs, _ := ch.Consume("order-processing", "", false /*autoAck*/, false, false, false, nil)
for m := range msgs {
    if err := handle(m.Body); err != nil {
        m.Nack(false, false) // не возвращать в очередь: уйдёт в DLX
        continue
    }
    m.Ack(false) // после этого сообщения в очереди больше нет
}

// Kafka (segmentio/kafka-go): пишем в топик, ключ задаёт партицию
w := &kafka.Writer{Addr: kafka.TCP("localhost:9092"), Topic: "orders", Balancer: &kafka.Hash{}}
err := w.WriteMessages(ctx, kafka.Message{Key: []byte("user-7"), Value: body})

// читаем в составе группы, offset коммитим после обработки
r := kafka.NewReader(kafka.ReaderConfig{
    Brokers: []string{"localhost:9092"}, GroupID: "billing", Topic: "orders",
})
for {
    m, err := r.FetchMessage(ctx)
    if err != nil { break }
    if err := handle(m.Value); err != nil { continue } // не коммитим: прочтём снова
    r.CommitMessages(ctx, m) // сдвинули закладку, сообщение из топика не пропало
}

Заметь: в Rabbit-коде сообщение «исчезает» по Ack, в Kafka-коде после CommitMessages оно лежит там же, просто закладка ушла вперёд.

Порядок

  • RabbitMQ: порядок гарантирован только в одной очереди при одном активном консьюмере. Несколько воркеров обработают сообщения в разном темпе, и порядок «поедет». Возврат в очередь (requeue) его тоже ломает.
  • Kafka: порядок строго гарантирован внутри одной партиции. Нужен порядок событий по пользователю — пишешь с ключом user_id, и все его события лежат в одной партиции по порядку. Между разными партициями порядка нет.

Что выбрать

RabbitMQ — когда есть работа, которую надо сделать один раз: письма, генерация PDF, биллинг-задачи, плюс сложная маршрутизация, приоритеты, RPC (Request-Reply).

Kafka — когда есть поток событий, который читают многие и, возможно, ещё раз: логи, метрики, кликстрим, Event Sourcing, наполнение DWH и аналитики несколькими системами.

Одна фраза-разделитель на собесе: «Очередь — это раздача работы, сообщение живёт, пока его не обработали. Топик — это журнал событий, сообщение живёт по сроку хранения, а читатели независимы и держат свой offset».

Частая ошибка на собесе

  • «Kafka — это такая очередь, только быстрее». Нет: у неё другая модель — лог с offset'ами, а не «забрал и удалил». Из-за этого иначе работают и replay, и fan-out, и масштабирование.
  • «Подтвердил сообщение в Kafka — оно удалилось». Нет: commit двигает только закладку консьюмера. Удаляет retention.
  • «Добавлю консьюмеров — прочитаем быстрее». В Kafka упрёшься в число партиций: лишние простаивают. Масштабирование — это сначала партиции, потом консьюмеры.
  • «В Rabbit можно перечитать сообщение через неделю». После ACK сообщения нет. Нужен replay — это аргумент в пользу Kafka.
  • Про порядок: не обещай «Kafka гарантирует порядок» без слов «внутри партиции».

Вне банка, для полноты: в свежих RabbitMQ есть тип Streams — журнал в духе Kafka. На собесе «RabbitMQ» почти всегда означает классические и quorum-очереди из этого урока.

Если что-то из этого осталось непонятным — просто спроси, разберём отдельно.
