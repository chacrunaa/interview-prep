Гарантии доставки — шпаргалка

Суть: exactly-once по сети невозможен. Реально: at-least-once + идемпотентный консьюмер.

ВидПотериДублиПолучается так
At-most-onceданетподтвердил → обработал; RabbitMQ auto_ack=true; Kafka автокоммит
At-least-onceнетдаобработал → подтвердил; ручной ACK / commit; ретраи продюсера
Exactly-onceнетнетat-least-once + идемпотентность (или транзакции Kafka внутри Kafka)

Продюсер

  • RabbitMQ: Publisher Confirms (ack после сохранения). Транзакции AMQP — устарели, в 100–250 раз медленнее.
  • Kafka: acks = 0 / 1 / all; retries без идемпотентности дают дубли; enable.idempotence=true (producer id + sequence number по партиции) убирает дубли ретраев.
  • Вне банка: min.insync.replicas для осмысленного acks=all.

Консьюмер

  • Порядок «обработал → подтвердил» = at-least-once. Обратный порядок = at-most-once.
  • Идемпотентность: таблица processed_messages(message_id PK), вставка и бизнес-логика в одной транзакции. Использовать ON CONFLICT DO NOTHING + RowsAffected, а не «любая ошибка = дубль».
  • Битое сообщение: лимит повторов + DLX, а не вечный requeue.

Exactly-once в Kafka

Идемпотентный продюсер + транзакции (transactional.id, begin/commit/abortTransaction) + консьюмер read_committed. Работает внутри Kafka (consume-transform-produce); внешнюю БД/HTTP не охватывает.

Из БД в брокер

Transactional Outbox: событие в таблицу outbox в одной транзакции с данными; relay (polling FOR UPDATE SKIP LOCKED или CDC/Debezium) отправляет в Kafka. Даёт at-least-once, поэтому получателю нужен Inbox.

Ловушки

  • «Kafka даёт exactly-once» без «внутри Kafka, в транзакциях».
  • Автокоммит ≠ надёжно: offset уходит до конца обработки.
  • Идемпотентный продюсер не защищает от повторной отправки из самого сервиса.
  • Отметка «обработано» и бизнес-эффект в разных транзакциях = дубль или потеря.
