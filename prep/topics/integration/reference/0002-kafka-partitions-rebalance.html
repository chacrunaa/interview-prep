Партиции и ребаланс — шпаргалка

Суть: топик — имя, физически есть только партиции. Партиция = упорядоченный append-only лог = единица порядка, параллелизма и репликации. Ребаланс — перераздача партиций внутри consumer group; его не отменяют, а делают редким и дешёвым.

Партиция

  • Offset уникален внутри партиции. Адрес сообщения: (partition, offset).
  • Порядок — только внутри партиции. Ключ → hash(key) % N → одна партиция.
  • Один консьюмер группы на партицию. Консьюмеров больше партиций — лишние простаивают.
  • Лидер (чтение/запись) + реплики; ISR — те, кто не отстал. Лидер умер — новый из ISR.
  • Партиций можно добавить, убавить нельзя; после добавления ключи «переезжают» (N изменилось).

Причины ребаланса

Консьюмер вошёл · умер (нет heartbeat дольше session.timeout.ms) · изменилась подписка. Вне банка: консьюмер не вернулся в poll() за max.poll.interval.ms.

Как смягчить

ПриёмСуть
CooperativeStickyAssignorДвигаются только нужные партиции, остальные читаются без остановки (в банке)
group.instance.id (вне банка)Статичное членство: рестарт в пределах session.timeout.ms ребаланса не вызывает
Тюнинг таймаутовsession.timeout.ms, heartbeat.interval.ms (≤ 1/3 session), max.poll.interval.ms, max.poll.records
onPartitionsRevokedДообработать и закоммитить до отзыва: нет дублей (в банке упомянут ConsumerRebalanceListener)
Дисциплина деплояНе гонять скейлинг вверх-вниз, не выходить за число партиций
KIP-848 (вне банка)Новый протокол: раздача на стороне координатора, без «стоп всей группе»

Ловушки

  • «Топик на одном брокере» — нет, партиции по разным.
  • «Ребаланса можно избежать» — нет, только минимизировать.
  • Heartbeat ≠ poll: зависшая обработка при живом heartbeat всё равно выкинет консьюмера.
  • Коммит после отзыва партиции бесполезен — коммитить надо до.
  • В Go кооперативный ребаланс зависит от библиотеки (проверить версию).
