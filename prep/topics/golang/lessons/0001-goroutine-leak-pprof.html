Утечка горутин: что это, как найти через pprof и как не допустить

Одна победа этого урока: ты объясняешь, почему горутина может «зависнуть навсегда», показываешь два классических примера в коде, называешь команду, которой утечка находится в проде, и три приёма, которыми её не допускают.

Опирается на golang/topic_07_concurrency.md («Как избежать утечек горутин», «Какими инструментами диагностировать утечку горутин», «for range по каналу, который никогда не закрывается», правило закрытия каналов) и golang/topic_09_dev_tools.md (раздел «pprof и профили»: goroutine profile, «Почему pprof показывает тысячи горутин waiting»). Всё, что не из банка, помечено «вне банка».

Аналогия

Горутина — это сотрудник, которого ты отправил с поручением. Он дошёл до двери, постучал и ждёт, что ему откроют. Если за дверью никого нет и не будет, он простоит там вечно: зарплату (память под стек) ему платят, а пользы ноль. Один такой сотрудник не страшен. Но если на каждый запрос к сервису ты отправляешь нового, через неделю у двери стоит толпа, а офис (память) закончился.

Главное отличие от обычного мусора: сборщик мусора (GC) такую горутину не уберёт. Она формально «жива», просто спит, а всё, на что она ссылается (буферы, соединения, данные запроса), остаётся в памяти вместе с ней.

Формально

Утечка горутины (по банку) — это ситуация, когда горутина блокируется навсегда: ждёт чтения из канала, в который никто не пишет, или записи в канал, который никто не читает. Рантайм не умеет понять, что ждать уже бесполезно, поэтому горутина живёт до конца процесса.

Типичные причины блокировки навечно:

  • запись в небуферизованный канал, у которого уже нет читателя (читатель ушёл по таймауту или по ошибке);
  • чтение из канала, который никто не закроет и в который никто не напишет;
  • for range ch, когда канал не закрывают: цикл выходит только после close (банк);
  • сетевой вызов без таймаута и без context (банк);
  • мьютекс или WaitGroup, которые никто не отпустит (вне банка).

Пример 1: запись в канал, которого уже никто не ждёт

func fetch() (int, error) {
    ch := make(chan int) // небуферизованный

    go func() {
        ch <- slowCall() // ждёт, пока кто-то прочитает
    }()

    select {
    case v := <-ch:
        return v, nil
    case <-time.After(time.Second):
        return 0, errors.New("timeout") // ушли, читать из ch больше никто не будет
    }
}

Если slowCall ответил позже секунды, функция уже вернула ошибку и ушла. Горутина досчитала результат и застряла на ch <- ... навсегда. Каждый таймаут оставляет одну такую горутину.

ch := make(chan int, 1) // буфер на 1: запись пройдёт, даже если читателя нет

Один этот символ чинит утечку: горутина кладёт результат в буфер и спокойно завершается, а канал соберёт GC.

Пример 2: воркер, который ждёт закрытия канала

func process(jobs <-chan Job) {
    go func() {
        for j := range jobs { // выйдет только после close(jobs)
            handle(j)
        }
    }()
}

Если владелец канала про close(jobs) забыл (например, вышел по ошибке), воркер ждёт следующую задачу вечно. Правило из банка: закрывает канал только отправитель. Если отправителей несколько, канал не закрывают, а отмену делают через done-канал или context.

Как обнаружить: от симптома к строке кода

Симптом утечки в проде: память процесса медленно растёт, число горутин в метриках ползёт вверх и не возвращается назад, а после деплоя всё сбрасывается. Дальше идёшь по шагам.

  1. Заметить рост. Логируй или выводи в метрики runtime.NumGoroutine(): если число постоянно растёт и не падает, это утечка (банк). Клиент Prometheus даёт метрику go_goroutines из коробки (вне банка).
  2. Подключить pprof. Пустой импорт import _ "net/http/pprof" и запущенный http.ListenAndServe (банк). Эндпоинты появятся по пути /debug/pprof/. На проде порт pprof не выставляют наружу: только во внутреннюю сеть или через port-forward (вне банка).
  3. Снять дамп. Два режима (банк):
    • /debug/pprof/goroutine?debug=1 — горутины сгруппированы по одинаковому стеку со счётчиком. Видно, например, «4800 горутин сидят на строке service.go:42».
    • /debug/pprof/goroutine?debug=2 — полный текстовый дамп каждой горутины с её состоянием (chan send, chan receive, semacquire) и, вне банка, сколько минут она так ждёт.
  4. Найти виновника. Тысячи горутин в состоянии ожидания на одной и той же строке — это и есть утечка (банк: «Почему pprof показывает тысячи горутин waiting»). Строка в стеке показывает, где именно застряли.
  5. Подтвердить сравнением. Вне банка: снимаешь два профиля с разницей во времени и смотришь, какой стек вырос: go tool pprof -base first.pb.gz second.pb.gz. Одна и та же группа, выросшая между снимками, и есть утечка.
// включение pprof в сервисе
import (
    "net/http"
    _ "net/http/pprof" // регистрирует /debug/pprof/* на DefaultServeMux
)

func main() {
    go func() {
        _ = http.ListenAndServe("localhost:6060", nil) // только локально
    }()
    // ... остальной сервис
}
curl 'http://localhost:6060/debug/pprof/goroutine?debug=1'
# 4800 @ 0x43a5f6 ...
# #   0x7a1b2c   myapp/service.fetch.func1+0x2c   service.go:42   <- все застряли тут

go tool pprof http://localhost:6060/debug/pprof/goroutine
(pprof) top          # у кого больше всего горутин
(pprof) list fetch   # исходник с подсветкой строки

Как предотвратить в коде

Один принцип на всё: перед запуском горутины знай, как и когда она завершится. Если ответа нет, это будущая утечка.

  1. Отмена через context. Горутина слушает ctx.Done() в каждой точке ожидания, а не только в начале (банк: «использовать context с таймаутами»). 
    go func() {
    select {
    case ch <- slowCall(ctx): // запись
    case <-ctx.Done():        // или отмена, если читателя уже нет
    }
}()
    Ключевое: и отправка, и получение в канал оборачивают в select с ctx.Done().
  2. Буфер там, где результат один. Канал на 1 элемент для единственного ответа (пример 1): отправитель никогда не заблокируется.
  3. Закрывает отправитель. Кто пишет в канал, тот его и закрывает, иначе for range у получателей не закончится (банк). Много отправителей: канал не закрывают, а отменяют через done или context.
  4. Таймауты на любой внешний вызов. HTTP-клиент, БД, брокер без таймаута держат горутину, пока на том конце не ответят (банк).
  5. Всегда вызывай cancel(). После WithCancel / WithTimeout пиши defer cancel(), иначе таймер и ссылка на родителя остаются в памяти (банк, «context leak»).
  6. Знать, кто ждёт горутину. Вне банка: sync.WaitGroup или errgroup (golang.org/x/sync/errgroup) с контекстом: функция не возвращается, пока все её горутины не закончились.
  7. Ловить в тестах. Вне банка: библиотека go.uber.org/goleak проверяет в конце теста, что лишних горутин не осталось (defer goleak.VerifyNone(t)).

Как ответить вслух

«Утечка горутины — это когда горутина навсегда заблокирована, например, пишет в канал, из которого никто не читает, или читает из канала, который никто не закроет, и GC её не уберёт, потому что она формально жива. Видно по тому, что число горутин и память растут и не падают. Нахожу так: подключаю net/http/pprof, снимаю /debug/pprof/goroutine?debug=1 и смотрю, на каком стеке сидят тысячи горутин, а debug=2 показывает состояние каждой. Предотвращаю так: контекст с таймаутом и select на ctx.Done() в каждой точке ожидания, канал закрывает отправитель, для одного результата делаю буфер на 1, и на любой внешний вызов ставлю таймаут».

Частая ошибка на собесе

  • «GC соберёт зависшую горутину». Нет: горутина — это живой «корень» для сборщика, он её не трогает и всё, на что она ссылается, тоже.
  • Путать с утечкой памяти от срезов. Это разные истории: слайс держит большой массив (банк, topic_08), а здесь держит горутина. Уточни, о какой речь.
  • Проверить ctx.Done() только в начале горутины. Заблокироваться можно потом, на отправке в канал. Проверять нужно в каждом месте ожидания.
  • Сказать «посмотрю по top» без pprof. Системные утилиты показывают только рост памяти, но не причину. Нужен именно goroutine-профиль со стеками.
  • Не знать разницу debug=1 и debug=2. Первый группирует по стеку (видно масштаб), второй даёт каждую горутину отдельно (видно состояние).
  • Выставить pprof наружу на проде. Эндпоинты показывают внутренности сервиса, их закрывают от внешней сети (вне банка).
Если что-то из этого осталось непонятным — просто спроси, разберём отдельно.
