sync.Once и sync.Pool: зачем нужны, реальные кейсы и разница

Одна победа этого урока: ты за минуту объясняешь простыми словами, что sync.Once отвечает на вопрос «сделать ровно один раз», а sync.Pool на вопрос «не создавать заново временные объекты», приводишь по реальному кейсу для каждого и не путаешь их.

Опирается на golang/topic_07_concurrency.md («Как работает sync.Once и какие у него гарантии», «Что такое sync.Pool», «Как sync.Pool взаимодействует со сборщиком мусора»), golang/topic_08_memory_runtime.md («В чём разница между sync.Pool и обычным кэшем», «Как оптимизировать код, чтобы уменьшить количество аллокаций») и topic_10_frameworks.md (fasthttp). Что не из банка, помечено «вне банка».

Аналогия

sync.Once — это табличка «Свет включён» на выключателе в общей комнате. Десять человек заходят одновременно, и каждый хочет включить свет. Первый включает, остальные видят табличку и просто ждут, пока он закончит. Свет включён один раз, никто не включил его дважды.

sync.Pool — это стопка одноразовых подносов в столовой. Берёшь поднос из стопки (Get), ешь, протираешь и возвращаешь (Put). Не нужно каждый раз покупать новый. Но уборщица (сборщик мусора) вправе в любой момент унести всю стопку, поэтому на подносе нельзя оставлять ничего ценного, а если стопка пуста, берёшь новый.

Общее у них только пакет sync и безопасность для горутин. Цели противоположные: Once про «ровно один», Pool про «сколько угодно, но дёшево», причём без гарантий.

sync.Once: реальные кейсы

Кейс 1. Ленивая инициализация общего ресурса. Клиент к базе, скомпилированная регулярка, загруженный конфиг: создавать дорого, нужен один на процесс, а запросы приходят параллельно.

var (
    once sync.Once
    db   *sql.DB
)

func getDB() *sql.DB {
    once.Do(func() {
        db, _ = sql.Open("postgres", dsn) // выполнится один раз
    })
    return db
}

Тысяча горутин одновременно вызвала getDB(): функция внутри Do отработает один раз, остальные 999 подождут и получат уже готовый db. Без Once пришлось бы вручную городить флаг и мьютекс и легко получить гонку.

Кейс 2. Идемпотентное закрытие. Повторный close(ch) вызывает панику. Если остановить сервис могут из нескольких мест, оборачиваем в Once:

type Server struct {
    stop     chan struct{}
    stopOnce sync.Once
}

func (s *Server) Stop() {
    s.stopOnce.Do(func() { close(s.stop) }) // сколько ни вызывай Stop, паники не будет
}

Нюансы (вне банка):

  • Пока первая горутина выполняет f, остальные блокируются и ждут. Долгую инициализацию в Once класть можно, но это пауза для всех.
  • Если f упала в панику, Once считает, что вызов состоялся: повторный Do уже ничего не запустит. Ошибку инициализации так не повторишь, её нужно сохранять отдельно.
  • Начиная с Go 1.21 есть удобные обёртки sync.OnceFunc, sync.OnceValue и sync.OnceValues: возвращают функцию, которая считает значение один раз.

sync.Pool: реальные кейсы

Проблема. Обработчик HTTP на каждый запрос создаёт буфер под тело ответа. Тысячи запросов в секунду дают тысячи короткоживущих буферов: куча растёт, GC запускается чаще и отнимает CPU. Пул позволяет взять уже выделенный буфер, использовать и вернуть (банк: «буферы при обработке HTTP запросов»).

var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) }, // что делать, если пул пуст
}

func render(data any) []byte {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()               // ОБЯЗАТЕЛЬНО: внутри могли остаться чужие данные
    defer bufPool.Put(buf)    // вернуть, когда закончили

    _ = json.NewEncoder(buf).Encode(data)

    out := make([]byte, buf.Len())
    copy(out, buf.Bytes())    // копия: буфер вернётся в пул и будет перезаписан
    return out
}

Где это встречается в реальности:

  • fasthttp (банк, topic_10): контексты запроса и ответа берутся из sync.Pool вместо создания новых на каждый запрос, отсюда низкое число аллокаций.
  • Буферы под чтение и сериализацию: bytes.Buffer, срезы байт под декодирование, батч-буферы (банк: «переиспользование больших буферов»).
  • Вне банка: стандартная библиотека сама использует пулы внутри (например, fmt для своих буферов форматирования).

Правила безопасного пула

  • Класть только пустые, легко пересоздаваемые объекты: буферы, структуры без состояния. Не соединения с БД и не объекты с важными данными: GC вправе очистить пул в любой момент (банк).
  • Сбрасывать перед использованием или перед Put (Reset, обнуление полей), иначе следующий получит остатки чужих данных (вне банка, но это самая частая ошибка).
  • Не использовать объект после Put: он уже может быть у другой горутины. Поэтому в примере результат копируется.
  • Не считать пул кэшем. Обычный кэш (Redis, map с LRU) хранит данные долго; пул это эфемерное хранилище, которое может опустеть в любой момент (банк).
  • Мерить. Пул не бесплатен и не всегда ускоряет. Смотри go test -bench . -benchmem: колонки B/op и allocs/op (банк).

Как не перепутать

СитуацияЧто брать
Создать клиент БД / загрузить конфиг лениво, один раз на процессsync.Once
Закрыть канал, даже если Stop вызовут несколько разsync.Once
На каждый запрос нужен временный буфер на 64 КБsync.Pool

Нужно ограничить число одновременных соединений с БДНе Pool: sync.Pool не ограничивает число объектов. Нужен пул соединений (database/sql) или семафор (вне банка)

Как ответить вслух

«sync.Once гарантирует, что функция в Do выполнится ровно один раз, даже если её одновременно вызовут тысячи горутин: остальные ждут, пока первая закончит. Использую для ленивой инициализации общего ресурса вроде клиента или конфига и для безопасного закрытия канала. sync.Pool это кэш переиспользуемых временных объектов, он снижает число аллокаций и нагрузку на GC, например на буферах в HTTP-обработчиках. Но GC может очистить пул в любой момент, поэтому туда кладут только пустые буферы, которые легко создать заново, и перед использованием сбрасывают. Разница: Once про корректность и гарантию «один раз», Pool про производительность и никаких гарантий».

Частая ошибка на собесе

  • «Pool это кэш». Нет: кэш хранит данные долго, пул может опустеть в любой момент. Данные с состоянием и важные объекты туда не кладут.
  • Положить в Pool соединение с БД. GC его заберёт, а пул не ограничивает количество объектов. Для соединений есть свой пул в database/sql.
  • Не вызвать Reset после Get. Следующий запрос увидит остатки данных предыдущего, а это ещё и утечка чужих данных между пользователями.
  • Использовать объект после Put. Он уже у другой горутины: гонка данных.
  • Думать, что Once можно «перезапустить». Нельзя: после первого вызова он выполнен навсегда, включая случай паники в f.
  • Класть в Once долгую операцию и удивляться паузе. Все остальные вызовы ждут её окончания.
  • Считать, что Pool всегда ускоряет. Для маленьких быстрых аллокаций выигрыша может не быть. Проверяют бенчмарком с -benchmem.
Если что-то из этого осталось непонятным — просто спроси, разберём отдельно.
