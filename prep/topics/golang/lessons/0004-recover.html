Как работает recover

Одна победа этого урока: ты объясняешь, что делает recover, почему он работает только внутри defer, почему панику в чужой горутине им не поймать, и где в реальном проде его ставят (а где нет).

Опирается на golang/topic_03_io_data.md («Чем panic отличается от error», «Когда использовать panic», «Как работает recover», «Можно ли использовать panic для управления потоком», «Почему recover работает только внутри defer»), golang/topic_07_concurrency.md («Что будет, если в горутине произойдёт паника», «Как правильно обрабатывать панику в горутине») и topic_10_frameworks.md (recovery middleware). Что не из банка, помечено «вне банка».

Аналогия

Паника — это пожарная тревога в здании. Все выходят по этажам сверху вниз, но перед выходом каждый успевает выполнить свой список «перед уходом»: выключить плиту, закрыть сейф (это defer). Если никто не вмешается, здание закрывается полностью (программа падает). recover — это дежурный, который стоит на одном из этажей, говорит «тревога ложная или локальная, я беру её на себя» и останавливает эвакуацию. Но стоять он может только в одном месте: в списке «перед уходом». В остальное время его там просто нет.

Формально

По банку, recover() — встроенная функция, которая останавливает процесс паники и возвращает значение, переданное в panic(). Работает только если вызвана напрямую внутри отложенной функции defer. В любом другом месте возвращает nil и ничего не останавливает.

Почему только внутри defer (банк). Когда случается паника, обычный поток обрывается, а выполняются только зарегистрированные defer (раскручивание стека). Обычный код после места паники просто не выполнится, поэтому вызывать recover там некому. Выполняются только отложенные функции.

Ход паники и recover по шагам

  1. Случилась паника (нехватка индекса, nil, panic("...")).
  2. Текущая функция останавливается, выполняются её defer в обратном порядке (последний зарегистрированный первым, вне банка).
  3. Если один из defer вызвал recover(), паника останавливается, recover возвращает её значение.
  4. Функция, в которой стоял этот defer, завершается и возвращается вызывающему как обычно. Код после места паники не продолжается.
  5. Если никто не вызвал recover, паника идёт вверх по стеку, дальше по тем же правилам. Дойдя до верха, она роняет программу.
func safeCall() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Recovered from panic:", r)
        }
    }()
    panic("something went wrong") // всё ниже не выполнится
    fmt.Println("сюда не дойдём")
}

Три правила, на которых ловят

1. Только напрямую в defer-функции

defer func() { recover() }()       // работает

defer recover()                    // вне банка: не ловит, recover вызван не из defer-функции

defer func() { helper() }()        // вне банка: если recover внутри helper, не ловит
func helper() { recover() }

Банк: «Если вызвать его вне функции, которую вызвал defer, он тоже не поймает панику».

2. Только в своей горутине

Паника в любой горутине роняет всё приложение, она не изолируется (банк). recover в родительской горутине не поймает панику в дочерней. Поэтому защита ставится внутри каждой горутины, где возможна паника, в самом начале:

go func() {
    defer func() {
        if r := recover(); r != nil {
            log.Println("Паника перехвачена:", r)
        }
    }()
    // опасный код
}()

3. Результат: функция возвращается, а не продолжается

После recover выполнение не «вернётся на строку после паники». Функция с этим defer завершается. Чтобы вызывающий узнал об ошибке, используют именованный возвращаемый результат (вне банка):

func parse(data []byte) (res Result, err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("parse panic: %v", r) // превращаем панику в error
        }
    }()
    return doParse(data), nil
}

Где recover ставят в реальном проде

Правило из банка: «Почти всегда используйте error. panic допустима только тогда, когда программа принципиально не может продолжать работу». А использовать панику для управления потоком выполнения — категорически нет, это анти-паттерн в Go. Поэтому recover это не инструмент обработки ошибок, а страховочная сетка на границах:

  • Recovery middleware в HTTP-сервере (банк, topic_10): ловит панику в обработчике и отдаёт 500 вместо падения всего сервиса. Вне банка: стандартный net/http сам перехватывает панику в хендлере, так что свой middleware нужен ради логов, метрик и своего формата ответа. Проверь по документации своей версии.
  • Верхний уровень горутины-воркера. Фоновая джоба, консьюмер очереди, воркер из пула: одна кривая задача не должна убивать процесс.
  • Демоны (банк, topic_07): «Всегда проверяйте ошибки и паники (через recover в демонах)».

Чего не делают: не оборачивают recover каждый вызов, не используют «поймал и поехали дальше» вместо обработки ошибок и не пишут recover() с пустым телом.

Что делать после перехвата

  • Залогировать с трассой стека (вне банка): log.Printf("panic: %v\n%s", r, debug.Stack()). Без стека невозможно найти причину.
  • Не глотать молча. Либо вернуть error вызывающему, либо ответить 500, либо отправить метрику.
  • Иногда лучше упасть. Если состояние программы после паники неизвестно (повреждённая общая память, незакрытые блокировки), перехват рискует оставить «полуживой» процесс. Тогда либо перезапуск, либо повторная паника через panic(r) (вне банка).

Что recover не поймает (вне банка)

  • Фатальные ошибки рантайма, например fatal error: concurrent map writes, нехватка памяти, переполнение стека горутины. Это не паники, и процесс падает без возможности перехвата.
  • Выход через os.Exit или log.Fatal: defer при этом вообще не выполняются.

Как ответить вслух

«recover останавливает панику и возвращает значение, которое передали в panic. Работает только внутри defer, потому что при панике выполняются только отложенные функции; в обычном коде он вернёт nil. После перехвата функция не продолжается с места паники, а завершается и возвращает управление вызывающему, поэтому ошибку обычно отдают через именованный результат. Ловит только панику своей горутины: паника в любой горутине роняет всё приложение, так что recover ставят внутри каждой горутины, где она возможна. В прикладной логике я ошибки возвращаю как error, а recover держу на границах: в middleware сервера и на верхнем уровне воркеров, и обязательно логирую со стеком».

Частая ошибка на собесе

  • Вызвать recover вне defer. Вернёт nil и ничего не остановит (банк).
  • Думать, что recover в main ловит панику в горутине. Нет: нужен свой defer recover в каждой горутине (банк).
  • Ждать, что выполнение продолжится после строки с паникой. Функция завершается.
  • Использовать panic/recover как try/catch. Анти-паттерн (банк): ошибки в Go идут значениями.
  • Ловить и молча игнорировать. Баг остаётся, а следов нет. Минимум: лог со стеком.
  • Не знать, что часть падений не перехватывается (concurrent map writes, OOM). Вне банка, но это любимый уточняющий вопрос.
  • Забыть, что после recover нужно как-то сообщить об ошибке. Для этого именованный результат err.
Если что-то из этого осталось непонятным — просто спроси, разберём отдельно.
